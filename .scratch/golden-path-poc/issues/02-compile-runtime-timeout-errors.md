# 02: Ошибки компиляции, runtime-ошибки и timeout

**What to build:** студент, сломавший код, всегда получает понятный Test Report вместо зависшей или упавшей страницы. Синтаксическая/типовая ошибка esbuild → `compile-error` со строкой и колонкой. Исключение на верхнем уровне модуля студента → `runtime-error`. Бесконечный цикл → `timeout` через 5 с, Sandbox уничтожается, следующий Run работает без перезагрузки страницы.

## Comments

**2026-10-03 — реализация (агент).** Ручной прогон в настоящем Chrome (dev): `while(true){}` → «Timed out» через ≈5.5 с, страница отзывчива; затем throw → «Runtime error» со stack, `a +;` → «Line 1, column 49: Unexpected ";"», правильное решение → 2 / 2 passed. iframe после Run не остаётся, внешних запросов — 0.

- **Главная находка: timeout работает, только если Sandbox живёт в отдельном процессе.** В Playwright-овском `chrome-headless-shell` (дефолт для headless) opaque-origin iframe делит renderer-процесс со страницей: `while(true){}` замораживает parent, никакой таймер в parent не срабатывает (проверено для `srcdoc`, `blob:`, `data:`; `--enable-features=IsolateSandboxedIframes` не помогает). Полный Chromium и Chrome 153+ выносят sandboxed iframe в отдельный процесс по умолчанию — тесты переведены на `channel: "chromium"`. Риск для отчёта PoC (тикет 05): Chrome не гарантирует изоляцию (memory pressure, Android); надёжная альтернатива — отдельный origin для Sandbox (вне скоупа PoC) или loop-guard-инструментация кода.
- Deadline один на весь Run, включая компиляцию и холодный `esbuild.initialize`. Если компиляция не вернулась к deadline — Worker `terminate()`, следующий Run создаёт новый. Настоящее зависание Worker'а реальным вводом не воспроизвести, поэтому тест использует `timeoutMs: 1` + зацикленный код и проверяет, что Sandbox после timeout не появляется (мутант без `terminate` этот тест валит).
- Колонки `compile-error` теперь 1-based (esbuild отдаёт 0-based).
- «Ошибка импорта» из чек-листа: при бандлинге все импорты статические, поэтому несуществующий модуль/экспорт — это `compile-error` от esbuild, а не `runtime-error`. `runtime-error` при импорте = исключение на верхнем уровне импортируемого модуля студента — покрыто тестом.

Не протестировано (на отдельный проход):
- Перекрывающиеся Run: timeout одного Run убивает общий Worker, и компиляция другого Run, ждущая в нём, теряется → тот тоже получит `timeout`. В UI не воспроизводится (кнопка заблокирована на время Run).
- Холодный старт входит в 5 с: на медленной машине первый Run может уйти в timeout, Worker пересоздастся и снова начнёт init с нуля. Сейчас cold Run ≈ 1 с.
- Асинхронное исключение во время выполнения тестов (например, throw в `setTimeout` внутри теста) превращает весь Run в `runtime-error` — результаты тестов теряются.
- `unhandledrejection` не слушаем: незахваченный reject в коде студента не ломает Run, но и не показывается.
- UI-отображение `runtime-error` и `timeout` — только ручной прогон; UI-тест есть для `compile-error`.
