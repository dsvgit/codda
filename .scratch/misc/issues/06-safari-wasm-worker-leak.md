# 06: Вкладка Safari грузит CPU и память: `esbuild.wasm` компилируется заново в каждом новом Worker

**What to build:** Открытое приложение не должно часами держать CPU и гигабайты памяти. Пересоздание Worker Compiler'а не должно запускать компиляцию `esbuild.wasm` заново. Браузер вне поддержки пилота должен честно сообщать, что он не поддерживается.

Что нашли (2026-10-05, человек и агент). У человека машину грузил процесс Safari `com.apple.WebKit.WebContent`: около 300% CPU и около 4 ГБ памяти 6 часов подряд, хотя `npm run dev` на `localhost:5173` был уже остановлен. Стеки `sample` показали:

- потоки `Wasm Worklist Helper Thread` в оптимизирующем компиляторе wasm у Safari (`JSC::Wasm::OMGPlan::work` → `allocateRegistersByGraphColoring`). `esbuild.wasm` — Go-бинарник около 10 МБ с огромными функциями, распределение регистров на них в Safari идёт очень долго;
- уничтоженный `WebCore: Worker`, который не может завершиться: `~VM()` ждёт в `JSC::Wasm::Worklist::stopAllPlansForContext`, пока доделается эта компиляция.

Почему это накапливается. `compiler.ts` уничтожает Worker при timeout Run'а, при отмене во время компиляции и при внутренней ошибке. Следующий Run создаёт новый Worker, и тот компилирует `esbuild.wasm` с нуля. В Chrome уничтоженный Worker умирает сразу. В Safari его компиляция продолжается в фоне, к ней добавляется новая. В Safari и первый Run медленный: он легко упирается в timeout 5 с, а timeout снова пересоздаёт Worker. Вероятно, отсюда и [тикет 05](05-compiler-non-build-error.md): при 4 ГБ wasm-процесс esbuild умирает.

Пилот рассчитан только на Chrome (`docs/roadmap.md`, «Определение MVP»), все тесты идут в Chromium. Поэтому порядок такой: сначала честное сообщение, потом устранение причины.

**Blocked by:** None (can start immediately)

**Status:** needs-info

Открытые вопросы (решить через `/grill-with-docs` в `.scratch/misc/questions/06-safari-wasm-worker-leak.md`, затем `ready-for-agent`):

1. **Сообщение о браузере.** Что делать вне Chrome: баннер «Поддерживается только Chrome» с возможностью продолжить или полный отказ? Как определять браузер: по User-Agent или по признаку движка?
2. **Один `WebAssembly.Module` на страницу.** Компилировать `esbuild.wasm` один раз в главном потоке (`WebAssembly.compileStreaming`) и передавать готовый модуль в каждый новый Worker через опцию `wasmModule` у `esbuild.initialize`. Нужно проверить в Safari и Chrome, что повторный `initialize` действительно не компилирует модуль заново и что оптимизированный код переиспользуется.
3. **Timeout без уничтожения Compiler.** Если компиляция уже закончилась и завис Sandbox, Worker Compiler'а можно оставить живым. Сейчас timeout и отмена всегда уничтожают его, если Run ещё в компиляции (`compiler.ts`, `onAbort`).

Критерии приёмки (черновик, уточняется вместе с вопросами):

- [ ] Вне Chrome экран показывает сообщение по ответу на вопрос 1. Компонентный тест подменяет признак браузера
- [ ] Пересоздание Worker Compiler'а не компилирует `esbuild.wasm` заново: модуль компилируется один раз на страницу. Тест Runner считает компиляции или загрузки `esbuild.wasm` после timeout и следующего Run
- [ ] Timeout в Sandbox после законченной компиляции не уничтожает Worker Compiler'а (если в вопросе 3 решено так)
- [ ] Ручная проверка в Safari: серия Run с timeout и отменой не оставляет фоновой нагрузки после закрытия или перезагрузки. Результат `sample` — в `## Comments`
- [ ] `npm run typecheck`, `npm test`, `npm run test:e2e` зелёные
