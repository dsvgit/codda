# Spec: runtime-hardening

**Status:** ready-for-agent — вопросы закрыты в [questions/00-grill.md](questions/00-grill.md) (все рекомендации приняты); source maps сняты из фичи решением Q11/Q13 [раундов 2–3](../questions/00-mvp-autorun.md).

Блок A roadmap, пункты 3.3–3.7 из [скоупа MVP](../../mvp/questions/00-map-round-2-scope.md): отмена Run, console студента, строка ошибки компиляции в Workspace, асинхронные ошибки во время тестов (R8 из [PoC Report](../../../docs/poc-report.md)), восстановление после падения Worker/Sandbox. Фича идёт второй в [порядке MVP](../README.md), после `lesson-manifest`: экран Lesson с тулбаром и нижней панелью (вкладки «Тесты» и «Решение») уже есть.

## Problem Statement

Runtime из PoC проходит Golden Path, но студент, у которого что-то идёт не так, остаётся без помощи:

- Run нельзя остановить. Если код завис или Run идёт слишком долго, студент ждёт 5 с до timeout.
- `console.log` в коде студента никуда не выводится. Самый привычный способ отладки не работает.
- Runtime-ошибка показывает stack бандла: номера строк относятся к скомпилированному коду вместе с React, а не к файлу студента. Ошибка компиляции показывает строку, но в редакторе её не видно, а если ошибка в Lesson Tests (например, студент переименовал экспорт), строка указывает в чужой файл.
- Исключение в `setTimeout` или незахваченный reject во время тестов превращает весь Run в `runtime-error`, и результаты всех тестов теряются (R8). Незахваченный reject вообще не виден.
- Если Worker Compiler'а упал или не смог загрузить `esbuild.wasm`, Run молча висит до timeout и советует искать бесконечный цикл. После неудачной загрузки `.wasm` Worker сломан навсегда: каждый следующий Run тоже уходит в timeout, пока не перезагрузить страницу.

## Solution

- Во время Run на месте `▶ Запустить тесты` стоит `■ Отмена` (решение [тикета 04 Плана](../../mvp/issues/04-lesson-screen-prototype.md)). Отмена сразу останавливает Run, во вкладке «Тесты» — «Запуск отменён», следующий Run работает как обычно.
- Нижняя панель получает вкладку «Console» между «Тесты» и «Решение» (порядок по тикету 04: Тесты · Console · Проблемы · Решение; «Проблемы» добавит `ts-tooling`). Там строки `console.log/info/warn/error/debug` из Sandbox за последний Run, по мере появления, со счётчиком строк на вкладке. Строки, выведенные до timeout или отмены, остаются видны.
- Ошибка компиляции в Workspace показывает `Строка N:M — сообщение` и подчёркивается в редакторе; ошибка компиляции вне Workspace показывается без строки. Runtime-ошибка показывает только сообщение, без stack бандла. Строка runtime-ошибки в файле студента (source maps) — «MVP, часть 2».
- Асинхронная ошибка во время теста валит этот тест, остальные выполняются (R8).
- Падение Worker Compiler'а сразу даёт понятный отчёт «Внутренняя ошибка», а не ложный timeout. Следующий Run поднимает новый Worker.

```
┌ ▶ Запустить тесты ┬ ↺ Сбросить ┬ Показать решение ─┐   во время Run: ■ Отмена
│ main.tsx (редактор)                               │
│   4 │ return count.map(…)    ← подчёркнуто при     │
│                               ошибке компиляции    │
├ Тесты 1/3 ┬ Console 2 ┬ Решение ──────────────────┤
│ ✗ increments — TypeError: count.map is not a …    │
│ ✗ decrements — expected "−1", got "0"             │
│ ✓ renders initial value                           │
└───────────────────────────────────────────────────┘
```

## User Stories

1. Как студент, я хочу остановить Run кнопкой `■ Отмена`, чтобы не ждать timeout, когда понял, что код завис.
2. Как студент, я хочу, чтобы `■ Отмена` стояла на месте «Запустить тесты», чтобы не искать её глазами.
3. Как студент, я хочу после отмены видеть «Запуск отменён», а не старый Test Report, чтобы не путать его с результатом последней версии кода.
4. Как студент, я хочу сразу после отмены снова запустить тесты и получить нормальный результат, без перезагрузки страницы.
5. Как студент, я хочу, чтобы отмена срабатывала и во время компиляции, а не только во время тестов.
6. Как студент, я хочу видеть вывод `console.log` своего кода, чтобы отлаживать решение привычным способом.
7. Как студент, я хочу видеть строки console по мере появления, чтобы понять, где зависает код, ещё до timeout.
8. Как студент, я хочу, чтобы строки, выведенные до timeout или отмены, не пропадали.
9. Как студент, я хочу отличать `console.warn` и `console.error` от обычного `console.log` по виду строки.
10. Как студент, я хочу видеть объекты и массивы в console в читаемом виде, а строки — без кавычек.
11. Как студент, я хочу видеть на вкладке «Console» число строк, чтобы знать, что там что-то есть, не открывая её.
12. Как студент, я хочу, чтобы console очищалась при каждом новом Run, чтобы не путать вывод разных попыток.
13. Как студент, я хочу, чтобы `console.log` в бесконечном цикле не вешал страницу, а показывал первые строки и сообщение, что остальное отброшено.
14. Как студент, я хочу видеть в runtime-ошибке понятное сообщение, а не stack скомпилированного бандла с чужими номерами строк.
15. ~~Строка у проваленного теста~~ — «MVP, часть 2» (source maps).
16. ~~Нет ложной строки у `expected … got …`~~ — без source maps строки у тестов нет вовсе.
17. ~~Строка кода студента при исключении внутри React~~ — «MVP, часть 2» (source maps).
18. Как студент, я хочу, чтобы строка с ошибкой компиляции подчёркивалась в редакторе, чтобы не считать строки вручную.
19. Как студент, я хочу, чтобы подчёркивание пропадало, когда я начинаю править код, чтобы оно не указывало на уже исправленное место.
20. Как студент, я хочу понятное сообщение без строки, если сломался импорт из моего файла в Lesson Tests (например, я переименовал экспорт), а не строку в файле, которого я не вижу.
21. Как студент, я хочу, чтобы ошибка в `setTimeout` или незахваченный reject во время теста валили только этот тест, а остальные результаты оставались.
22. Как студент, я хочу видеть незахваченный reject как ошибку теста, а не терять его молча.
23. Как студент, я хочу, чтобы исключение на верхнем уровне моего модуля по-прежнему давало runtime-ошибку, потому что тесты тогда не могут запуститься.
24. Как студент, я хочу, чтобы при падении компилятора мне сказали «внутренняя ошибка, попробуйте ещё раз», а не советовали искать бесконечный цикл.
25. Как студент, я хочу, чтобы после неудачной загрузки компилятора (например, сеть моргнула) следующий Run работал без перезагрузки страницы.
26. Как студент, я хочу, чтобы текст timeout называл реальные причины (бесконечный цикл, зависший промис, нехватка памяти), а не только цикл.
27. Как владелец платформы, я хочу, чтобы parent принимал от Sandbox только сообщения ожидаемой формы с правильным `runId` и игнорировал всё остальное (ADR-0003), включая строки console.
28. Как владелец платформы, я хочу, чтобы parent сам ограничивал число строк console за Run, а не полагался на Sandbox.
29. Как разработчик, я хочу, чтобы каждый сценарий (отмена, console, строки, async-ошибки, падение Worker) проверялся браузерным тестом на шве Runner, чтобы Runtime можно было менять без страха.
30. Как Author, я хочу, чтобы `codda test` (он гоняет тот же Runtime, тикет 05 Плана) видел те же строки и async-ошибки, что и студент.

## Implementation Decisions

- **Интерфейс Runner** остаётся одной функцией и расширяется опциями:
  ```ts
  run(input, { timeoutMs?, signal?, onConsole? }) → Promise<TestReport>
  ```
  `signal` — внешний `AbortSignal` отмены; `onConsole(line)` вызывается на каждую строку console текущего Run. Deadline и отмена идут одним путём: уничтожить Sandbox, а если Run ещё компилируется — `terminate()` Worker (как timeout в PoC). Следующий Run создаёт новый.
- **Форма Test Report** (меняется; строки и колонки — 1-based, всегда в файле Workspace):
  ```ts
  type TestResult = { name: string; status: "pass" | "fail"; error?: string };
  type TestReport =
    | { kind: "tests"; results: TestResult[] }
    | { kind: "compile-error"; errors: { message: string; line?: number; column?: number }[] }
    | { kind: "runtime-error"; message: string }
    | { kind: "timeout"; ms: number }
    | { kind: "cancelled" }
    | { kind: "internal-error"; message: string };
  type ConsoleLine = { level: "log" | "info" | "warn" | "error" | "debug"; text: string };
  ```
  `stack` из `runtime-error` уходит: бандл-stack студенту не нужен. Строку runtime-ошибки в Workspace добавят source maps в «MVP, часть 2»; тогда `line/column` появятся у `runtime-error` и `TestResult`.
- **Протокол postMessage** (ADR-0003): к единственному `codda:report` добавляется `{ type: "codda:console", runId, level, text }`. Канал — `MessagePort`: Sandbox создаёт `MessageChannel` и первым сообщением `codda:port` через `window.postMessage` передаёт порт, Runner проверяет у него `event.source === iframe.contentWindow` и `runId`. `codda:report` и `codda:console` идут через порт, у каждого Runner проверяет `runId` и форму полей; всё прочее игнорирует. Причина: Chrome не доставляет `window.postMessage` от iframe, пока тот крутит синхронный цикл, а порт доставляет сразу (решение человека, 2026-10-04, runtime-hardening/02). После `codda:report`, отмены и timeout порт закрывается, поздние сообщения не доходят. Поле `stack` в `codda:report` не передаётся.
- **Console в Sandbox:** Test Harness до кода студента подменяет `console.log/info/warn/error/debug` и шлёт каждую строку сразу. Аргументы — через пробел; строки как есть, прочее — тем же форматированием, что и сообщения `expect` (`{"items":[1,2]}`, `NaN`, `-0`), `Error` — как `String(err)`. Лимиты: не больше 1000 строк за Run и 10 000 символов на строку; на 1001-й строке Sandbox шлёт одну строку «Console: показаны первые 1000 строк, остальное отброшено» уровня `warn` и замолкает. Runner применяет тот же лимит со своей стороны (граница доверия). Перехватывается всё, что пишет Sandbox: код студента, Lesson Tests, предупреждения React.
- **Асинхронные ошибки (R8):** Test Harness слушает `error` и `unhandledrejection` весь Run. Пока выполняется тест — от вызова до конца его промиса плюс один macrotask после (`setTimeout(0)`, чтобы долетели ошибки из таймеров с нулевой задержкой и reject'ы после микрозадач), — ошибка валит этот тест (если он ещё не упал сам) и он продолжает считаться законченным, когда закончится его промис. До `runAll` (верхний уровень модулей) — `runtime-error`, как в PoC. После последнего теста отчёт уходит, и Sandbox уничтожается: поздние ошибки не видны. Текст ошибки — как у синхронного throw: `message` для `Error`, `String(x)` для прочего.
- **Ошибки компиляции:** `line/column` есть только у ошибок, чей `location.file` — Workspace. Ошибка в Lesson Tests (например, `No matching export in "main" for import "add"`) показывается без строки. Сообщения esbuild остаются английскими. Строка берётся из `location` esbuild, source map для этого не нужен.
- **Подчёркивание в редакторе:** редактор Workspace получает от экрана Lesson диагностики Run (ошибки компиляции с `line/column`) и показывает их через `@codemirror/lint` (зависимость из списка `README.md`). Диагностика подчёркивает от позиции до конца строки. Сбрасывается на старте следующего Run и на первой правке документа. `ts-tooling` позже добавит в тот же редактор диагностики Type Checker; два источника не должны затирать друг друга — это его забота, здесь источник один.
- **Падение Worker Compiler'а:** Worker отвечает `{ id, error }`, если `compile` бросил вне esbuild (не загрузился `.wasm`, упал `initialize`), а Runner слушает ещё и событие `error` самого Worker (не загрузился скрипт). В обоих случаях Worker уничтожается, Run сразу возвращает `internal-error`, следующий Run создаёт новый Worker и заново грузит `.wasm`. Автоматического повтора нет. Падение процесса Sandbox (например, нехватка памяти) отдельно не ловится: его покрывает timeout, текст которого перечисляет причины.
- **Экран Lesson:**
  - Тулбар: пока Run идёт, вместо `▶ Запустить тесты` — `■ Отмена`; нажатие отменяет Run через `signal`.
  - Вкладка «Тесты»: `cancelled` — нейтральный «Запуск отменён» (не красный); `internal-error` — красный заголовок «Внутренняя ошибка», сообщение и «Запустите тесты ещё раз»; ошибки компиляции — `Строка N:M — сообщение` (без строки — только сообщение); `runtime-error` — «Ошибка выполнения» и сообщение, без stack; `timeout` — «Тесты не завершились за N с: бесконечный цикл, зависший промис или нехватка памяти».
  - Вкладка «Console»: строки за текущий Run, у `warn`/`error` свой цвет; счётчик строк на вкладке; очищается на старте Run; после Run открывается «Тесты», как решено в тикете 04.

## Testing Decisions

- **Хороший тест** проверяет внешнее поведение: «отдал Workspace + Lesson Tests (+ отменил / подписался на console) → получил такой Test Report и такие строки console», а не вызовы esbuild, VLQ-декодер или DOM Sandbox.
- **Главный шов — Runner `run()`** в Vitest browser mode на полном Chromium, prior art — тесты Runner из PoC (мини-задание `add` прямо в файле теста, проверка «iframe не остался», «следующий Run работает» после timeout). Через него идут отмена, console, строки, async-ошибки и падение Worker. Ошибки и граничные случаи — в том же тикете, где поведение появляется (правило MVP).
- **Второй шов — экран Lesson** в Vitest browser mode (prior art — UI-тест PoC: рендер приложения, клик по кнопке, `expect.element(page.getByText(…))`): кнопка `■ Отмена`, вкладка «Console» со счётчиком, тексты ошибок, подчёркивание в редакторе. Только то, что не видно на шве Runner.
- **e2e (Playwright, offline-фикстура)** — только где нужна собранная сборка или управление сетью: сорванная загрузка `esbuild.wasm` через `page.route` → «Внутренняя ошибка» → следующий Run проходит. Prior art — e2e Golden Path и `offline`-фикстура.
- Подделка сообщений Sandbox тестируется изнутри: код студента читает `__coddaRunId` и шлёт `parent.postMessage` неверной формы — Runner его игнорирует.
- Каждый тикет зелёный по `typecheck`, unit и e2e.

## Out of Scope

- Прогрев Worker и холодный старт вне deadline (R1), защита от бесконечных циклов вне Chrome (R3), preview/HMR — «MVP, часть 2».
- Timeout отдельного теста: зависший промис в тесте по-прежнему съедает весь Run до timeout.
- Обнаружение падения процесса Sandbox (OOM) иначе, чем timeout.
- Source maps: строка runtime-ошибки и проваленного теста в Workspace (Q11/Q13 [раундов 2–3](../questions/00-mvp-autorun.md), «MVP, часть 2» в `docs/roadmap.md`).
- Переход к строке по клику на `Строка N:M`, подчёркивание runtime-ошибок в редакторе, инспектор объектов в console, `console.table/group/time`, привязка строк console к тесту.
- Перевод сообщений esbuild и Test Harness на русский.
- Security baseline: Sandbox может подделать отчёт, зная `runId` (оценка в браузере — на доверии, ADR-0004); CSP и отдельный origin — блок F.
- Вкладка «Проблемы» и диагностики Type Checker — `ts-tooling`.

## Further Notes

- **Согласование с соседями.** `lesson-manifest` строит вкладку «Тесты» и, возможно, уже показывает ошибку компиляции как `Строка N:M — сообщение` по тикету 04; тогда здесь меняется только смысл строки (только Workspace), добавляется подчёркивание, а у runtime-ошибки убирается stack. `author-cli` (`codda test`) должен обработать новые виды отчёта `cancelled` (не бывает без `signal`) и `internal-error` (ошибка инфраструктуры, код выхода как у сбоя, а не FAIL). `ts-tooling` подключает свои диагностики к тому же `@codemirror/lint` в редакторе.
- Имя Workspace в Compiler — `./main` (договорённость 3 `README.md`); по нему ошибка компиляции отличает Workspace от Lesson Tests.
