# runtime-hardening — вопросы

Grilling по фиче [runtime-hardening](../spec.md): отмена Run, console, source maps, асинхронные ошибки во время тестов (R8), восстановление после падения. [План решений](../../../mvp/map.md) прямо оставил вопросы про async-ошибки, отмену и source maps на эту фичу; кнопка `■ Отмена`, вкладка «Console» со счётчиком и формат `Строка N:M — сообщение` уже решены [тикетом 04](../../../mvp/issues/04-lesson-screen-prototype.md) и здесь не обсуждаются. ## Раунд 1

### Q1 — Кому достаётся асинхронная ошибка во время тестов (R8)

Сейчас исключение в `setTimeout` во время тестов превращает весь Run в `runtime-error`, результаты всех тестов теряются, а незахваченный reject не виден вовсе. Варианты:

- **(a) Текущему тесту.** Test Harness слушает `error` и `unhandledrejection`. Ошибка, пришедшая, пока идёт тест (до конца его промиса и ещё один macrotask, чтобы долетели таймеры с нулевой задержкой), валит этот тест; остальные выполняются. Ошибка на верхнем уровне модуля — `runtime-error`, как сейчас. Ошибка после последнего теста не видна: отчёт уже ушёл. Минус: таймер, запущенный в одном тесте и сработавший в следующем, свалит следующий.
- **(b) Run целиком, но с результатами.** Отчёт `tests` плюс отдельный блок «Необработанные ошибки», Run считается FAIL (как в Vitest). Честнее про «чей таймер», но студент не видит, какой тест виноват, а Test Report получает новый раздел.
- **(c) Как сейчас, но с уже готовыми результатами:** `runtime-error`, к которому приложены результаты тестов до ошибки. Остальные тесты не выполняются.

➡️ **Рекомендация:** (a). У студента ошибка почти всегда в коде, который вызвал текущий тест, а форма Test Report не меняется. Случай «таймер перетёк в следующий тест» редкий и всё равно даёт FAIL с понятным сообщением.

### Q2 — Что видит студент после отмены Run

Нажатие `■ Отмена` уничтожает Sandbox, а если Run ещё компилируется, то и Worker (как timeout в PoC). Следующий Run тогда платит холодный старт, около 1 с. Что показать во вкладке «Тесты»:

- **(a)** Нейтральное «Запуск отменён» (не красное); строки console, выведенные до отмены, остаются. Runner возвращает новый вид отчёта `cancelled`.
- **(b)** Вернуть предыдущий Test Report, будто Run не было. Но он относится к старой версии кода и может показать PASS, которого уже нет.
- **(c)** Пустую вкладку.

Отдельно: при отмене во время компиляции можно не убивать Worker, а просто не ждать его ответа. Тогда холодного старта нет, но зависшая компиляция продолжит занимать Worker, и следующий Run встанет за ней в очередь.

➡️ **Рекомендация:** (a), Worker при отмене во время компиляции уничтожается, как при timeout: один путь вместо двух, а тёплая компиляция длится миллисекунды, так что отменяют её почти только тогда, когда она действительно зависла.

### Q3 — Console: когда показывать и сколько

- **Когда.** (a) Строки идут из Sandbox по одной и появляются во вкладке сразу. Так видно, где зависает код, ещё до timeout или отмены. (b) Строки приходят одним пакетом вместе с Test Report. Проще, но при timeout и отмене вывод теряется, а именно тогда он нужнее всего.
- **Что.** Всё, что пишет Sandbox: код студента, Lesson Tests, предупреждения React (например, про `act`). Отфильтровать «чужое» надёжно нельзя.
- **Сколько.** `while (true) console.log(1)` за 5 с шлёт миллионы сообщений и вешает parent. Лимит: 1000 строк за Run и 10 000 символов на строку; дальше одна строка «Console: показаны первые 1000 строк, остальное отброшено». Лимит проверяют и Sandbox, и Runner.
- **Вид.** `log/info/debug` обычные, `warn`/`error` цветом; строки без кавычек, объекты как JSON (то же форматирование, что в `expected … got …`). Без инспектора объектов, без `console.table/group`, без привязки к тесту.

➡️ **Рекомендация:** (a), всё из Sandbox, лимиты 1000 строк / 10 000 символов, вид как выше.

### Q4 — Какую строку показывать у ошибки

Source map сопоставляет stack бандла с файлом Workspace. Но в стеке бывают кадры Lesson Tests, Test Harness и React. Правила:

- `runtime-error` и проваленный тест: `Строка N:M` берётся из **первого кадра стека, попавшего в Workspace**. Кадры Lesson Tests, Test Harness и Dependency Artifact пропускаются. Поэтому ошибка внутри React, вызванная компонентом студента, указывает на компонент.
- Тест, упавший на `expect(…)`, не имеет кадров Workspace, поэтому показывается без строки: только `expected 5, got -1`. Строку в Lesson Tests не показываем, ведь студент этот файл не видит.
- Ошибка компиляции получает строку и подчёркивание в редакторе, только если она в Workspace. Ошибка в Lesson Tests, например `No matching export in "main" for import "add"` после переименования экспорта, показывается без строки.
- Bundle-stack из Test Report убираем совсем. Сейчас UI показывает его при runtime-ошибке, но студенту он не нужен.
- Подчёркивание ошибки компиляции снимается на первой правке и на следующем Run. Runtime-ошибки не подчёркиваются (как в тикете 04), переход к строке по клику не делаем.

➡️ **Рекомендация:** как в списке выше.

### Q5 — Падение Worker Compiler'а

Сейчас, если `esbuild.wasm` не загрузился или `initialize` упал, Run молча висит до timeout с советом искать бесконечный цикл. Хуже того, Worker после этого сломан навсегда: каждый следующий Run тоже уходит в timeout, пока не перезагрузить страницу. Варианты:

- **(a)** Сразу отчёт нового вида `internal-error`: «Внутренняя ошибка», сообщение, «Запустите тесты ещё раз». Worker уничтожается, следующий Run поднимает новый. Автоповтора нет.
- **(b)** Как (a), но Runner один раз сам повторяет Run на новом Worker и показывает ошибку, только если упал и повтор. Студент реже видит ошибку, но Run может длиться вдвое дольше, а повтор приходится вписывать в deadline.

Падение процесса Sandbox (например, нехватка памяти) отдельно не ловим. Его покрывает timeout, текст которого меняется на «Тесты не завершились за 5 с: бесконечный цикл, зависший промис или нехватка памяти».

➡️ **Рекомендация:** (a). Сбой редкий, кнопка рядом, а повтор усложняет deadline ради пилота только в Chrome.

## Предложения в общие документы

Сам эти файлы не трогаю. Применить после ответов на раунд 1.

**`CONTEXT.md`:**

- **Test Report** — дополнить: «…либо ошибка компиляции, runtime-ошибка, timeout, отмена Run или внутренняя ошибка Runtime». Ошибки в нём указывают строку в файле Workspace.
- Новый термин **Console** (раздел «Работа студента» или «Исполнение»): вывод `console.*` из Sandbox за один Run — кода студента, Lesson Tests и зависимостей; показывается во вкладке «Console». _Avoid_: лог, output, stdout.
- **Run** — «Одно нажатие «Run tests»» → «Одно нажатие «Запустить тесты»…; Run можно отменить», если это ещё не сделал `lesson-manifest`.

**ADR:** новых не нужно. Решения обратимы и локальны для Runtime. Протокол `codda:console` укладывается в ADR-0003 (postMessage с проверкой формы). При желании одной строкой в Consequences ADR-0003 можно перечислить типы сообщений Sandbox → parent: `codda:report`, `codda:console`.
