## Problem Statement

Студент пишет TypeScript/TSX в редакторе, который о типах ничего не знает. Опечатку в имени хука, неверный тип пропса или забытый `return` он узнаёт только после Run, по непонятному падению теста или runtime-ошибке. esbuild типы не проверяет. Подсказок нет: чтобы вспомнить, что возвращает `useReducer` или какие методы у `HTMLElement`, нужно идти в документацию. Roadmap обещает в MVP «базовые подсказки TypeScript (diagnostics, autocomplete для React)».

Author тоже не узнаёт об ошибках типов в Solution и Lesson Tests: `codda test` проверяет только, что они собираются и проходят. Ошибка типов в Solution всплывёт у студента на вкладке «Решение».

При этом всё должно работать без единого внешнего запроса (ADR-0002). Стандартные решения (`createDefaultMapFromCDN`, ATA) тянут lib-файлы и `.d.ts` с CDN, а `typescript@^7`, который стоит в проекте для `tsc -b`, в браузере не запускается.

## Solution

**Type Checker** — отдельный Web Worker на TypeScript 6 (`typescript-6`, алиас на `typescript@6.0.3`) и `@typescript/vfs`. Он подчёркивает ошибки типов в редакторе Workspace и даёт autocomplete. lib-файлы TS приходят одним JSON-файлом с нашего origin, `.d.ts` зависимостей — из `types.json` Dependency Artifact Course.

Что видит студент:

- Через 1–2 с после открытия Lesson ошибки TS подчёркиваются красным. Наведение показывает сообщение по-английски с кодом: `Type 'number' is not assignable to type 'string'. (TS2322)`. После правки подчёркивания обновляются через ~300 мс.
- В нижней панели появляется вкладка **«Проблемы»** со счётчиком ошибок и списком `строка:колонка — сообщение (TSxxxx)`. Клик по строке ставит курсор в это место редактора. Пока Type Checker грузится, на вкладке «…» и «Проверка типов загружается». Если он не загрузился или упал — «Проверка типов недоступна».
- При наборе и по Ctrl/Cmd+Space появляется список подсказок от TS: имена из области видимости, члены объекта после `.`, экспорты `react`. У каждой подсказки есть вид и короткая сигнатура.
- Run от Type Checker не зависит: работает до его готовности, при ошибках типов и при его отказе. Lesson засчитывается только по Lesson Tests.

Что видит Author: `codda test` проверяет типы тем же TS 6 и тем же конфигом. Ошибка типов в Solution или Lesson Tests — ошибка Lesson (`✗`, код выхода `1`). Ошибка типов в Starter — предупреждение (`⚠`), код выхода от неё не меняется.

Compiler, Type Checker и проверка типов в `codda test` берут параметры TS из одного модуля конфига.

```
┌ тулбар: ▶ Запустить тесты · ↺ Сбросить · Показать решение ─────────┐
│ main.tsx                                                           │
│  3   const [open, setOpen] = useState(false);                      │
│  4   setOpen("yes");                                               │
│              ~~~~~  Argument of type 'string' is not assignable…   │
├ Тесты · Console · Проблемы 1 · Решение ────────────────────────────┤
│ 4:11 — Argument of type 'string' is not assignable to parameter    │
│        of type 'SetStateAction<boolean>'. (TS2345)                 │
└────────────────────────────────────────────────────────────────────┘
```

## User Stories

1. Как студент, я хочу видеть ошибки типов подчёркнутыми прямо в редакторе, чтобы исправлять их до Run.
2. Как студент, я хочу видеть текст ошибки при наведении на подчёркивание, чтобы понять, что не так.
3. Как студент, я хочу видеть у ошибки код `TSxxxx`, чтобы найти её объяснение поиском.
4. Как студент, я хочу, чтобы подчёркивания обновлялись вскоре после того, как я перестал печатать, а не на каждую букву, чтобы редактор не мигал.
5. Как студент, я хочу, чтобы синтаксические ошибки тоже подчёркивались, чтобы не ждать Run ради пропущенной скобки.
6. Как студент, я хочу не видеть подсказок-«шума» (неиспользуемая переменная, «можно сделать async»), чтобы Starter не выглядел сломанным с первой секунды.
7. Как студент, я хочу, чтобы типы React (`useState`, `useReducer`, JSX-атрибуты) проверялись так же, как в настоящем проекте, чтобы учиться на реальных ошибках.
8. Как студент, я хочу, чтобы современные API (`toSorted`, `Object.groupBy`) не считались ошибкой, раз они работают в моём браузере и при Run.
9. Как студент, я хочу видеть ошибку `Cannot find module`, если импортирую пакет, которого нет в Course, чтобы понять это до Run.
10. Как студент, я хочу видеть вкладку «Проблемы» с числом ошибок, чтобы знать, всё ли чисто.
11. Как студент, я хочу видеть все ошибки списком `строка:колонка — сообщение (TSxxxx)`, чтобы не искать их глазами по файлу.
12. Как студент, я хочу кликнуть по ошибке в списке и попасть курсором в нужное место, чтобы быстро её исправить.
13. Как студент, я хочу видеть «Проблем нет», когда ошибок нет, чтобы отличать «чисто» от «ещё не проверено».
14. Как студент, я хочу видеть «Проверка типов загружается», пока Type Checker стартует, чтобы не думать, что ошибок нет.
15. Как студент, я хочу видеть «Проверка типов недоступна», если Type Checker не загрузился или упал, и спокойно продолжать работу.
16. Как студент, я хочу запускать тесты в любой момент, даже при ошибках типов и до готовности Type Checker, чтобы посмотреть, что падает на недописанном коде.
17. Как студент, я хочу, чтобы Lesson засчитывался по Lesson Tests, даже если Type Checker недоволен, чтобы ложная ошибка меня не блокировала.
18. Как студент, я хочу, чтобы редактор открывался сразу, а Type Checker догружался после, чтобы не ждать 1–2 с перед началом работы.
19. Как студент, я хочу, чтобы при переходе к другому Lesson проверка работала сразу, без повторной долгой загрузки.
20. Как студент, я хочу, чтобы после «Сбросить» ошибки пересчитались для Starter.
21. Как студент, я хочу, чтобы на вкладке «Решение» не было подчёркиваний и Solution не попадала в счётчик «Проблемы», чтобы видеть только свои ошибки.
22. Как студент, я хочу получать подсказки имён при наборе, чтобы не помнить API наизусть.
23. Как студент, я хочу вызывать подсказки по Ctrl/Cmd+Space, чтобы посмотреть, что доступно в этом месте.
24. Как студент, я хочу после `.` видеть члены объекта (методы массива, поля события, свойства DOM-элемента), чтобы писать без документации.
25. Как студент, я хочу видеть в подсказке вид (функция, переменная, свойство) и короткую сигнатуру, чтобы выбрать нужное.
26. Как студент, я хочу видеть один список подсказок, а не два смешанных, чтобы не путаться в дублях.
27. Как студент, я хочу, чтобы выбранная подсказка заменяла уже набранный префикс, а не дописывалась к нему.
28. Как студент, я хочу не видеть подсказок внутри строк и комментариев, чтобы они не мешали писать текст.
29. Как владелец платформы, я хочу, чтобы Type Checker не делал ни одного запроса за пределы нашего origin, чтобы соблюдался ADR-0002.
30. Как владелец платформы, я хочу, чтобы падение Type Checker не ломало редактор и Run, чтобы вспомогательная функция не роняла основную.
31. Как владелец платформы, я хочу один Type Checker на сессию, чтобы не тратить по ~70 МБ памяти и 1–2 с на каждый Lesson.
32. Как Author, я хочу, чтобы `codda test` падал на ошибке типов в Solution, чтобы студент не увидел её на вкладке «Решение».
33. Как Author, я хочу, чтобы `codda test` падал на ошибке типов в Lesson Tests, чтобы тесты были такими же строгими, как код.
34. Как Author, я хочу получать предупреждение `⚠` об ошибке типов в Starter, но с кодом выхода `0`, чтобы заглушки в Starter были допустимы, а случайные ошибки — заметны.
35. Как Author, я хочу видеть ошибку типов с путём от корня Course, строкой, колонкой, сообщением и кодом, чтобы сразу открыть нужный файл.
36. Как Author, я хочу видеть ошибки типов вместе со всеми остальными ошибками Lesson за один прогон, чтобы не запускать `codda test` по кругу.
37. Как Author, я хочу, чтобы `codda test` и редактор студента показывали одни и те же ошибки типов, чтобы «в CI чисто» значило «у студента чисто».
38. Как Author, я хочу, чтобы Lesson, созданный `codda init` или `codda lesson`, проходил проверку типов без предупреждений.
39. Как Author, я хочу, чтобы пакет без типов давал `any`, а не ошибку типов, раз `codda test` уже предупредил о нём.
40. Как разработчик инструмента, я хочу один модуль конфига TS для Compiler, Type Checker и `codda test`, чтобы `target` и `jsx` менялись в одном месте.
41. Как разработчик инструмента, я хочу, чтобы Type Checker имел узкий интерфейс (файл → diagnostics, completions), чтобы позже заменить TS 6 на TS 7 в WASM, не трогая редактор.
42. Как разработчик инструмента, я хочу, чтобы `tsc -b` (TS 7) продолжал проверять код инструмента, а TS 6 использовался только в браузере и `codda test`.

## Implementation Decisions

### Модули

- **Конфиг TS** (новый, без зависимостей, импортируется из браузерного кода и из CLI в Node без сборки). Экспортирует параметры в виде tsconfig-JSON: `target: "ESNext"`, `lib: ["ESNext", "DOM", "DOM.Iterable"]`, `module: "ESNext"`, `moduleResolution: "bundler"`, `jsx: "react-jsx"`, `strict`, `isolatedModules`, `skipLibCheck`, `noEmit`, `types: []`. `noUnusedLocals` и `noUnusedParameters` не включаются. Compiler передаёт эти параметры в esbuild (`tsconfigRaw` и `target: "esnext"`) вместо своих `jsx: "automatic"` и умолчаний. Type Checker и `codda test` переводят их в программный вид через `ts.convertCompilerOptionsFromJson` из TS 6 (так `lib` превращается в имена файлов и не ловит `TS6054`).
- **Loader по расширению** (передано из `lesson-manifest`). Compiler сейчас компилирует всё с `loader: "tsx"`, а в `main.ts` это ломает `<T>value` и generic-стрелки `<T>(x: T) => x`. Compiler выбирает loader по расширению файла: `.ts` → `ts`, `.tsx` → `tsx`, для Workspace и для Lesson Tests. Type Checker и так различает их по имени файла.
- **Ядро проверки типов** (новое; общее для Type Checker и `codda test`, работает и в Worker, и в Node). Вход: lib-файлы, содержимое `types.json`, файлы Lesson (`путь → текст`). Внутри — `createSystem` + `createVirtualTypeScriptEnvironment` из `@typescript/vfs` с `ts` из `typescript-6`, переданным явно. `createDefaultMapFromCDN`, `createDefaultMapFromNodeModules` и ATA не используются. Наружу три операции:
  - заменить или создать файл (при смене Lesson меняется только файл, окружение не пересоздаётся; если у нового Starter другое расширение, старый файл удаляется);
  - ошибки файла: syntactic + semantic, только `category === Error`, suggestion-diagnostics не запрашиваются. Каждая ошибка — `{ from, to, line, column, message, code }`, `message` склеен из цепочки `messageText`, `line`/`column` 1-based;
  - подсказки в позиции: `getCompletionsAtPosition`, без auto-import (`includeCompletionsForModuleExports: false`). Каждая подсказка — `{ label, kind, detail }`, плюс диапазон заменяемого префикса. Внутри строк и комментариев список пуст.
- **lib-файлы TS.** Список файлов выводится из конфига TS (`knownLibFilesForCompilerOptions` или замер `program.getSourceFiles()`), берутся они из пакета `typescript-6`, чтобы версии lib и компилятора совпадали. При сборке UI они кладутся в один JSON (`виртуальный путь → текст`) с content-hash в имени, рядом с остальными ассетами UI. В режиме разработки Vite отдаёт тот же JSON. `codda test` в Node читает те же файлы прямо из пакета `typescript-6`, по тому же списку.
- **Type Checker** (новый Web Worker, отдельный от Compiler). Получает от страницы адрес JSON с lib-файлами и адрес `types.json` текущего Dependency Artifact (того же `deps/<hash>/`, из которого читает Compiler). Загружает их один раз, строит окружение ядра и отвечает на сообщения `{ id, … }` так же, как Compiler: `diagnostics(file, text)` и `completions(file, text, pos)`. Каждый запрос несёт полный текст файла, поэтому синхронизации состояния редактора с воркером нет. При ошибке загрузки сообщает `failed` и больше ничего не делает.
- **Клиент Type Checker** (новый, на странице, рядом с клиентом Compiler). Один воркер на сессию, создаётся после первой отрисовки экрана Lesson, вне React-компонента редактора, поэтому пересоздание `EditorView` его не перезапускает. Отдаёт статус `loading | ready | unavailable` и те же два вызова. `unavailable` — при `failed` от воркера или событии `error` у воркера, в том числе позже, посреди сессии. Повторных попыток нет. Запросы, отправленные до готовности, ждут её; в `unavailable` они сразу возвращают пустой результат.
- **Обвязка CodeMirror** (новая, тонкая, по образцу `@valtown/codemirror-ts`, но без него). Подключается только к редактору Workspace, не к read-only редактору вкладки «Решение».
  - `linter(source, { delay: 300 })` из `@codemirror/lint`: источник спрашивает diagnostics у клиента и отдаёт их CodeMirror с `severity: "error"` и сообщением `<message> (TS<code>)`. Те же diagnostics уходят в состояние экрана для вкладки «Проблемы».
  - `autocompletion({ override: [tsSource] })` из `@codemirror/autocomplete`: единственный источник — TS, keyword-completion `lang-javascript` в список не попадает. Подсказки при наборе и по Ctrl/Cmd+Space; у пункта `label`, `type` (из `kind`) и `detail`. Без JSDoc, auto-import и signature help.
  - Имя файла в Type Checker — имя Starter текущего Lesson (`main.ts` или `main.tsx`).
- **Вкладка «Проблемы»** нижней панели экрана Lesson (вкладку добавляет эта фича, договорённость 4 в `README.md`). Счётчик на вкладке: `…` в `loading`, число ошибок в `ready`, без числа в `unavailable`. Содержимое: «Проверка типов загружается» / список `строка:колонка — сообщение (TSxxxx)` / «Проблем нет» / «Проверка типов недоступна». Клик по строке ставит курсор в начало ошибки и фокусирует редактор. После Run по-прежнему открывается «Тесты». В `unavailable` подчёркивания из редактора убираются.
- **Run** не меняется: он не ждёт Type Checker и не смотрит на его ошибки. Test Report и засчитывание Lesson — только по Lesson Tests (ADR-0009).
- **Проверка типов в `codda test`** (дополнение к шагам фичи `author-cli`). Идёт после сборки Dependency Artifact, в Node, через ядро проверки типов, lib-файлы из `typescript-6` и `types.json` только что собранного артефакта. Если артефакт не собрался, Lesson не проверяются (как и сейчас). Для каждого Lesson два прогона:
  - **Solution + Lesson Tests:** Solution лежит в окружении под именем Starter (`main.*`), потому что Lesson Tests импортируют `./main`, рядом — Lesson Tests и объявление `@codda/test`. Любая ошибка в любом из двух файлов — ошибка Lesson. В выводе путь — настоящий файл Lesson (`<lesson>/solution.tsx`, `<lesson>/lesson.test.tsx`), а не виртуальное имя.
  - **Starter:** только файл Starter, ровно как его видит студент в редакторе (Q1 в [questions/00-grill.md](questions/00-grill.md)). Ошибка — предупреждение, Lesson получает `⚠`, если других ошибок нет.
  - Оба прогона идут независимо от Run: и когда Solution не прошёл Lesson Tests (тогда `author-cli` не запускает Starter в Chromium), и при ошибках Run. Lesson с ошибкой манифеста не проверяется ни в Chromium, ни по типам.
  - Формат строки — как у остальных ошибок `codda test`: под строкой Lesson с отступом, `<путь от корня Course>:<строка>:<колонка> — <сообщение> (TS<код>)`. Ошибки типов выводятся вместе с ошибками Run этого Lesson, Run из-за них не пропускается. Источник добавляется в вердикт Lesson из `author-cli` («ошибки и предупреждения»), предупреждения Starter попадают в итоговое «K предупреждений».
  - `codda dev` и `codda build` типы не проверяют. Служебная страница `codda test` в Chromium Type Checker не запускает.
- **Объявление `@codda/test`.** Lesson Tests импортируют `test` и `expect` из `@codda/test`. Для проверки типов инструмент несёт `.d.ts` этого модуля, написанный по публичному API Test Harness. `tsc -b` проверяет, что Test Harness ему соответствует, чтобы они не разъехались. В браузерный Type Checker объявление не попадает: студент Lesson Tests не правит.
- **`types.json`** собирает `dependency-artifacts` (договорённость 5 в `README.md`, формат — в [спеке dependency-artifacts](../03-dependency-artifacts/spec.md), раздел «Формат `deps/<hash>/`»): плоский объект `виртуальный путь → текст` с путями `/node_modules/<пакет>/…`, для пакета без типов — заглушка в `/node_modules/@types/<имя>/…`. Ядро кладёт его в окружение как есть, без преобразований. Адрес — поле `deps` в `course.json` плюс `types.json`. Если `deps` равно `null` (Course без импортов пакетов), Type Checker работает только с lib-файлами.

### Зависимости

- `typescript-6` (`npm:typescript@6.0.3`, точная версия) и `@typescript/vfs` — в `dependencies` пакета `codda`: они нужны и UI, и CLI в рантайме. `typescript@^7` остаётся для `tsc -b`.
- `@codemirror/lint` и `@codemirror/autocomplete` — явными зависимостями, в версиях, которые уже стоят через `codemirror` (`basicSetup`). Второй экземпляр `@codemirror/state` или `@codemirror/view` ломает расширения.
- Других новых зависимостей нет.

## Testing Decisions

Хороший тест проверяет поведение, видимое студенту или Author: подчёркивание и текст ошибки в редакторе, строки вкладки «Проблемы», пункты списка подсказок, строки вывода и код выхода `codda test`. Внутренности (сообщения воркеру, форма окружения vfs) не проверяются. Ошибки и граничные случаи тестируются в том же тикете, что и основной путь (правило MVP из `CLAUDE.md`).

Швы, сверху вниз:

1. **e2e Playwright на экране Lesson** (основной шов для браузера). Prior art: `e2e/golden-path.e2e.ts` и фикстура `e2e/offline.ts`, которая валит тест на любом внешнем запросе. Поэтому каждый e2e этой фичи заодно проверяет ADR-0002 для Type Checker. Отказ и медленную загрузку Type Checker тест имитирует через `page.route` на JSON с lib-файлами или на скрипт воркера. Число воркеров и запросов — через `page.on("worker")` и журнал запросов фикстуры. Lesson берётся из пилотного курса React Hooks, текст вводится через `fill`, как в существующих e2e.
2. **`codda test` как процесс** (шов для проверки типов Author). Prior art — тесты CLI фичи `author-cli`: временная копия курса-фикстуры, запуск `codda test`, проверка stdout и кода выхода. Фикстуры с ошибкой типов в Solution, в Lesson Tests и в Starter создаются правкой копии в тесте. CI репозитория уже гоняет `codda test` по `courses/` (фича `author-cli`), это заодно проверяет, что Solution всех пяти Lesson React Hooks чисты по типам.
3. **Ядро проверки типов** — unit-тесты (Vitest, как `src/runtime/runner.test.ts`) только для граничных случаев, которые дорого ловить через e2e: склейка цепочки сообщений, 1-based колонки на многострочном коде, смена расширения файла, пустые подсказки в строке и комментарии.

Компонентный тест экрана (`src/App.test.tsx`, Vitest browser) остаётся для Run. Type Checker в нём не нужен, поэтому он не должен ломать этот тест своим отсутствием или медленным стартом.

## Out of Scope

- Hover (кроме сообщения ошибки), go to definition, форматирование — «MVP, часть 2».
- Auto-import, signature help, JSDoc в подсказках — «MVP, часть 2».
- Строка «Есть ошибки типов: N» в Test Report и баннере PASS — «MVP, часть 2».
- Warnings и suggestions TS, `noUnused*`.
- Русские сообщения TS (решено: английские с кодом, Q6 тикета 09).
- Повторные попытки загрузки Type Checker, прогрев, кэширование разобранных lib между сессиями.
- Type Checker на вкладке «Решение» и для Lesson Tests в браузере.
- Multi-file: в окружении ровно один файл студента.
- TS 7 в браузере, `@codemirror/lsp-client`.
- Проверка типов в `codda dev` и `codda build`.

## Further Notes

- **Две TypeScript в одном пакете.** Любой код, который импортирует голый `typescript`, получит TS 7 без JS-API. Ядро всегда получает `ts` из `typescript-6` явно. У `@typescript/vfs` peer-зависимость на `typescript`, её удовлетворяет TS 7, это безвредно, пока `ts` передаётся аргументом.
- **Node без сборки.** CLI запускается как `.ts` через type stripping Node 24, поэтому модуль конфига и ядро не используют `enum`, `namespace` и параметры-свойства и импортируют соседей с расширением `.ts`.
- **`@typescript/vfs` в браузерной сборке** содержит `require("path")` и `require("fs")` для Node-функций. Vite подставляет пустые заглушки, но это стоит проверить на первой сборке воркера (research §2).
- Цена из research: ~1.1 МБ br (воркер ~781 КБ, lib ~284 КБ, типы React ~77 КБ), холодный старт 1–2 с, ~70 МБ памяти, перепроверка ~50 мс. В e2e ожидание первых diagnostics укладывается в `expect.timeout` 10 с.
- Устаревший ответ linter'а (текст изменился, пока воркер считал) CodeMirror отбрасывает сам, по версии документа. Проверять это руками не нужно.
