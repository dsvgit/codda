## Раунд 1

### Q1 — Как устроена служебная страница прогонов в `codda test`

Решено, что `codda test` выполняет Run на служебной странице собранного UI (тикет 05, Q4). Не решено, как именно Node управляет прогонами. Варианты:

- **(a) Фрагмент `#/__codda-test` того же `index.html` с API для Playwright.** На этом фрагменте UI загружает `course.json` и выставляет в `window` две функции: `warmUp()` и `run(lessonId, "solution" | "starter") → Test Report`. Run идёт тем же Runtime и тем же путём «Lesson → вход Compiler», что и кнопка «Запустить тесты». Node вызывает их по очереди через `page.evaluate` и печатает строку Lesson сразу после его проверки. С id Lesson фрагмент не пересекается: `_` не входит в kebab-case.
- **(b) Отдельный HTML-вход** (например, `codda-test.html`) во второй точке входа Vite. API такое же. В обычной сборке появляется второй HTML-файл. Изоляция от экрана Lesson лучше, но служебная страница не проверяет, что `index.html` вообще поднимается.
- **(c) Без служебной страницы: Playwright кликает настоящий UI.** Тест открывает `#/<lesson id>`, вставляет Solution в редактор, жмёт «Запустить тесты» и читает вкладку «Тесты». UI проверяется заодно, но тест зависит от разметки, которую меняют `runtime-hardening`, `ts-tooling` и `course-ux`. Test Report приходится восстанавливать из DOM, а каждый Run медленнее.

➡️ **Рекомендация:** (a). Это самая маленькая добавка к UI, Run проходит ровно тем путём, что у студента, а Test Report приходит в Node как данные, без разбора DOM. Настоящий UI и так проверяют e2e инструмента.

### Q2 — Добавляет ли `codda init` сам `codda` в `devDependencies` курса

По тикету 05 `codda init` создаёт `package.json` «без зависимостей». После misc/03 курс вызывает `npx codda` и подключает `codda` как `devDependency`. Если `init` его не добавит, `npx codda test` в новом курсе не найдёт локальный `codda`. В репозитории курса `npx` тогда скачает какую-нибудь версию из registry (после публикации) или упадёт (до неё). Шаблоны CI тоже рассчитывают на `npm ci` → `npx codda`.

- **(a)** `init` добавляет `codda` в `devDependencies`. Если пакет запущен не из `node_modules` (этот репозиторий), записывается `file:` с относительным путём до `packages/codda`. Иначе записывается точная версия запущенного `codda`. `npm install` после `init` ставит его без сети (`file:`) или из registry `.npmrc` (после misc/04). `dependencies` остаются пустыми, Dependency Artifact это не задевает (ADR-0007 игнорирует `devDependencies`).
- **(b)** Как в тикете 05: `package.json` без зависимостей, а Author сам выполняет `npm install -D codda`. Подсказка об этом печатается в конце `init`.

➡️ **Рекомендация:** (a). Тогда свежий курс сразу проходит `npx codda test` (критерий тикета 05) и CI из шаблона, а версия `codda` зафиксирована в lockfile курса.

### Q3 — Что выкладывается на Pages, если курсов в `courses/` несколько

Тикет 06: `codda test` и `codda build` идут по каждой папке с `course.yaml`, а одна сборка — один курс. Сайт на Pages один, адрес пилота `https://dsvgit.github.io/codda/` не меняется. Сейчас курс один, но правило нужно уже в `ci.yml`.

- **(a)** Пилотный курс задан одной переменной в начале workflow (`courses/react-hooks`). Его `dist/` отдаётся из корня Pages, остальные курсы только проверяются. Адрес пилота не меняется.
- **(b)** Каждый курс выкладывается в `/<course id>/`, корень Pages пуст или отдаёт простой список. Пилот переезжает на `…/codda/react-hooks/`. `localStorage` от этого не теряется (origin тот же), но ссылки меняются, и нужна страница-список, которой в MVP нет.
- **(c)** Если курсов больше одного, CI падает.

➡️ **Рекомендация:** (a). Адрес пилота сохраняется, второй курс не требует ничего, кроме проверки, а выкладку нескольких курсов можно решить, когда второй курс появится.

## Предложения в общие документы

**`CONTEXT.md`** — новый термин в разделе «Авторинг»:

> **Сборка Course** (Course Build):
> Папка статических файлов, которую выдаёт `codda build`: готовый UI, `course.json` и Dependency Artifact в `deps/<hash>/`, с маркером `.codda-build`. Её же проверяет `codda test` и раздаёт `codda dev`; одна сборка — один Course.
> _Avoid_: dist, бандл, билд

**ADR:** нового не нужно. В Consequences ADR-0008 стоит дописать строку: «Служебная страница прогонов `#/__codda-test` входит в готовый UI; `codda test` управляет ею из Node через Playwright (`warmUp`, `run`)» — если Q1 = (a).

**`docs/roadmap.md`**, «MVP, часть 2»:

- Выкладка нескольких курсов на один сайт пилота (если Q3 = (a)).
- Один `npm ci` вместо двух в CI курса. Сейчас `npm ci` нужен до `npx codda`, а `codda test` при `CI=true` повторяет его (тикет 05, Q6). Решение — при `CI=true` проверять свежесть `node_modules`, а не переустанавливать.

**`docs/HOW-TO-PROCEED.md`**, строка 4: выкладка на Pages берёт `dist/` пилотного курса из `codda build` (делает тикет 06 фичи).
