### Q11 — Форма манифеста артефактов: больше вариантов

Что нужно Runtime для Lesson: ① какой URL у каждого specifier'а, ② `integrity` каждого файла, включая chunk'и, ③ где лежит типовой артефакт для Type Checker. Пусть «папка набора» — это `deps/<setHash>/`, где `setHash` — ключ кэша сборки (см. Q14).

- **(a) Один общий `deps-manifest.json`** (вариант из Q9): все наборы и таблица «Lesson → набор». Runtime грузит один файл на всё приложение. Минусы: собственная схема, файл растёт с числом наборов, и при изменении любого набора меняется общий файл.
- **(b) Стандартный import map на набор.** В папке набора лежит `importmap.json` строго по спецификации HTML (`imports` + `integrity`), рядом `types.json`. Lesson в собранном виде знает только свой `setHash`. Своей схемы почти нет: в варианте 2 файл вставляется в `srcdoc` как есть, в варианте 3 те же поля читает Worker. Минус: на открытие Lesson нужен ещё один маленький запрос, если набор ещё не загружен.
- **(c) Import map прямо в данных Lesson.** `codda build` кладёт в собранный Lesson поле `importMap` и URL типов, отдельного манифеста нет. Lesson самодостаточен, лишнего запроса нет. Минусы: одна и та же карта копируется во все Lesson набора (несколько КБ), и формат собранного Lesson начинает зависеть от формата артефактов.
- **(d) Манифест на набор в своей схеме:** `deps/<setHash>/manifest.json` с `specifiers`, `files` (`path → sha384`), `types` и метаданными (версии пакетов, `mode`, версия esbuild). Import map Runtime строит из него сам. Плюсы: удобная отладка («какие версии в этом наборе?»), в одном месте можно хранить данные для `codda test`. Минус: своя схема и шаг преобразования.

➡️ **Рекомендация:** (b). Стандартный формат не требует документировать свою схему, и он одинаково подходит обоим транспортам. Метаданные для отладки при желании можно положить отдельным `meta.json` в той же папке, Runtime его не читает.

## Раунд 3

### Q17 — Упростить: зависимости только на уровне Course

Откуда сложность. Почти вся новая инфраструктура из раунда 2 нужна только потому, что Lesson может добавить свои зависимости. Из-за этого наборов несколько, нужны lockfile на каждый набор, таблица «Lesson → набор», правило «повтор пакета — ошибка» и отдельный термин Dependency Set.

Почему без этого можно обойтись. Если `zustand` нужен одному Lesson, его можно объявить на уровне Course, и остальные Lesson ничего не потеряют. С import map браузер скачивает только те модули, которые реально импортированы. Lesson, где нет `import "zustand"`, этот пакет не скачает и не исполнит. Цена — только чуть более долгая сборка в CI. Конфликт «двум Lesson нужны разные версии одного пакета» в одном курсе по одной теме на практике не возникает.

Про вашу идею из Q12 («lockfile только у Lesson, с учётом зависимостей Course»). Сделать так можно, но тогда lockfile нужен **каждому** Lesson: в пилоте это 5 почти одинаковых файлов. Транзитивные версии в них со временем разъедутся, у каждого Lesson окажется своя сборка React, и общего артефакта не будет. Это сложнее, а не проще.

Варианты:

- **(a) Оставить как решено:** наборы Course ∪ Lesson, lockfile'ы генерирует `codda` (Q12–Q14).
- **(b) Только Course, формат прежний:** `dependencies` остаются в `course.yaml`, а из frontmatter `lesson.md` убираются. `codda` генерирует один `course.lock.json`. Набор один, таблица «Lesson → набор» не нужна.
- **(c) Только Course, обычный npm:** в корне Course лежат стандартные `package.json` (в `dependencies` точные версии) и `package-lock.json`. Автор ставит пакеты обычным `npm install react@19.3.0`, а lockfile ведёт сам npm. `codda` lockfile'ы не генерирует, только читает. `dependencies` убираются и из `course.yaml`, и из `lesson.md`. Попутно редактор автора получает `node_modules` с типами, а registry из `.npmrc` работает сам собой (ADR-0006).

Что остаётся при любом варианте: CJS-обёртки, проверка «работает в браузере», типовой артефакт, import map. Это и есть суть ADR-0005, от неё не уйти.

Что меняется в (c) относительно уже решённого. Тикет 03 придётся поправить: из `course.yaml` и frontmatter уходит `dependencies`. Q4 и Q13 решаются стандартно: lockfile — это `package-lock.json`, обновляет его `npm install`, а в CI `npm ci` сам падает, если lock устарел. Q12 отпадает. Q5 остаётся в силе: `@types/react` объявляется в `package.json`. Диапазоны версий (`^19.3.0`) `codda test` по-прежнему считает ошибкой. Чтобы npm сам писал точные версии, в шаблон курса кладётся `.npmrc` с `save-exact=true`.

➡️ **Рекомендация:** (c). Своя инфраструктура lockfile'ов исчезает полностью: npm делает это лучше, а авторы с ним уже знакомы. Если Lesson-уровень когда-нибудь понадобится, его можно добавить в «MVP, часть 2».

## Общий итог

Открытых вопросов не осталось. Решение целиком:

1. **Объявление зависимостей.** Только на уровне Course, в стандартных `package.json` (`dependencies`, точные версии) и `package-lock.json` в корне Course. Ведёт их npm, `.npmrc` с `save-exact=true` входит в шаблон курса. Диапазон версий — ошибка `codda test`. `devDependencies` `codda` игнорирует. У Lesson своих зависимостей нет.
2. **Гранулярность.** Один Dependency Artifact на Course: `npm ci` и один `esbuild.build` (`format: "esm"`, `splitting`, `platform: "browser"`, conditions с `development`, `NODE_ENV=development`). Только dev-сборка.
3. **Точки входа** выводятся из импортов Starter, Solution и Lesson Tests всех Lesson. Импорт любого другого specifier'а даёт compile-error «не предусмотрен заданием».
4. **CJS → ESM (R9).** Имена экспортов берутся через `require()` в Node, обёртка добавляет `export default` = `module.exports`. Если пакет падает в Node, `codda test` выдаёт ошибку с именем пакета.
5. **Формат.** `deps/<hash>/` содержит `importmap.json` строго по спецификации HTML (`imports` + `integrity` sha384 на все файлы), `types.json` и файлы с content-hash в именах. Hash — от `package-lock.json`, точек входа, версии esbuild, конфига сборки (с `mode`) и версии пайплайна.
6. **Транспорт в MVP — как в PoC.** Worker скачивает файлы по `importmap.json`, проверяет `integrity` и вшивает их в бандл на каждом Run. R4 принимается. Эксперимент 07 и import map в `srcdoc` (варианты 2 и 3) переносятся в «MVP, часть 2».
7. **Типы.** `@types/*` из `dependencies` попадают только в `types.json`. Если у пакета нет типов, `codda test` выдаёт подсказку с именем `@types` для объявления. Пакет совсем без типов даёт предупреждение и становится `declare module` (`any`).
8. **«Работает в браузере».** Ошибка сборки на Node built-ins с понятным текстом. Все Chromium-прогоны `codda test` блокируют запросы не на наш origin. Статический скан отложен.
9. **Ошибки npm** показываются как есть, с префиксом `npm ci:` и одной подсказкой от `codda`.

Документы: новый ADR-0007, ссылка на него в ADR-0005, правки `CONTEXT.md` (Dependency Artifact, Course), тикеты 03, 05 (Lesson Tests выполняются в Chromium), 06 (CORS не нужен), 07 (отложен), 08 (Answer, resolved), `map.md`, roadmap.
