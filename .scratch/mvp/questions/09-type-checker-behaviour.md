## Раунд 1

### Q1 — Подтвердить вариант B из research

Type Checker работает в отдельном Web Worker, не вместе с Compiler. Внутри TypeScript 6 и `@typescript/vfs`, без `createDefaultMapFromCDN` и без ATA. lib-файлы отдаются JSON-артефактом с нашего origin, к CodeMirror подключается своя тонкая обвязка. Интерфейс воркера узкий: `setFile` / `diagnostics` / `completions`. Позже, когда у TS 7 появится WASM/LSP, реализацию за этим интерфейсом можно будет заменить.

Как подключить TS 6 рядом с TS 7, который остаётся для `tsc -b`:

- **(a)** npm-алиас `"typescript-6": "npm:typescript@6.0.3"`. Версия точная, ровно та, что замерена в research, и lib-файлы берутся из того же пакета.
- **(b)** Официальный `@typescript/typescript6@6.0.2`. Он сделан для сценария «TS 7 рядом с API 6.0», но внутри у него диапазон `@typescript/old: npm:typescript@^6`, и точная версия фиксируется только lock-файлом.

➡️ **Рекомендация:** вариант B, подключение (a). Алиас прозрачнее, а версия TS видна прямо в `package.json`.

### Q2 — Блокирует ли ошибка типов Run

esbuild типы не проверяет, поэтому Compiler соберёт код и с ошибками типов.

- **(a) Run работает всегда.** Ошибки типов видны только как подчёркивания в редакторе и на вкладке «Проблемы». Студент может запустить тесты на недописанном коде и посмотреть, что падает. Ровно так работают Vite/esbuild в реальных проектах.
- **(b) Run блокируется.** Пока есть ошибки типов, кнопка «Запустить тесты» неактивна или по нажатию открывает «Проблемы». Это строже и учит читать ошибки TS. Минусы: Run зависит от готовности Type Checker (холодный старт 1–2 с, Q4), и студент застревает, если ошибка ложная или непонятная.
- **(c) Run работает, но предупреждает.** Тесты запускаются, а в Test Report добавляется строка «Есть ошибки типов: N → Проблемы».

➡️ **Рекомендация:** (a). Type Checker помогает студенту, но не судит его: оценку ставят Lesson Tests. Вариант (c) можно добавить позже, если в пилоте студенты будут игнорировать подчёркивания.

### Q3 — Общий `target` и один источник конфига

Сейчас Compiler собирает в `esnext` (по умолчанию esbuild), а research предлагает для Type Checker `ES2022`. Из-за этого синтаксис и API новее ES2022, например `arr.toSorted()` (ES2023) или `Object.groupBy` (ES2024), подчёркиваются как ошибка, хотя в Chrome работают.

- **(a) Всё `ESNext`:** у Type Checker `target: ESNext` и `lib: esnext + dom + dom.iterable`, esbuild остаётся с `esnext`. Код студента исполняется только в актуальном Chrome (пилот — только Chrome).
- **(b) Всё `ES2022`:** у esbuild явно `target: "es2022"`, у Type Checker `lib.es2022`. Это консервативнее, но студент получает ложные ошибки на современные API.

В обоих вариантах параметры (`target`, `lib`, `jsx`, `strict`, `isolatedModules`, `moduleResolution`…) живут в одном модуле. Его читают Compiler, Type Checker и `codda test`, чтобы три места не разъехались.

➡️ **Рекомендация:** (a) плюс один общий модуль конфига. Когда понадобятся Safari или Firefox, `target` поднимется для всех трёх в одном месте.

### Q4 — Когда грузить Type Checker и что видно до его готовности

Цена: ~1.1 МБ br (воркер ~781 КБ, lib ~284 КБ, типы React ~77 КБ), холодный старт 1–2 с в браузере, ~70 МБ памяти. `types.json` один на Course (ADR-0007), поэтому при переходе между Lesson окружение пересоздавать не нужно, достаточно заменить файл.

- **(a) Один воркер на сессию, старт при открытии Course** после первой отрисовки экрана (сначала редактор, потом Type Checker). При смене Lesson меняется только содержимое файла.
- **(b) Ленивый старт после первого ввода в редакторе.** Экономит трафик тем, кто только читает Instructions, зато подчёркивания появляются через 1–2 с после начала набора, когда студент уже пишет код.
- **(c) Отдельный воркер на каждый Lesson.**

Что видит студент, пока Type Checker не готов: редактор полностью работает, просто без подчёркиваний и подсказок. На вкладке «Проблемы» вместо счётчика стоит «…», а внутри написано «Проверка типов загружается». Если воркер не загрузился или упал, там же появляется «Проверка типов недоступна», а Run и редактор продолжают работать. Повторных попыток в MVP не делаем.

### Q5 — Какие diagnostics показывать

TS отдаёт три вида: syntactic, semantic (ошибки) и suggestion (подсказки вроде «можно сделать async» или «переменная не используется»). Starter часто содержит неиспользуемые импорты и параметры-заглушки, а в `codda test` они дают только предупреждение.

- **(a) Только ошибки** (syntactic + semantic, `category === Error`). `noUnusedLocals` и `noUnusedParameters` выключены, suggestion-diagnostics не запрашиваем. Счётчик «Проблемы» = число ошибок.
- **(b) Ошибки плюс warnings/suggestions** другим стилем (жёлтое или блёклое подчёркивание). Это шумнее, и в Starter студент сразу видит «проблемы», которых не создавал.

Также: diagnostics пересчитываются с debounce ~300 мс после последнего нажатия. Вкладка «Проблемы» показывает список `строка:колонка — сообщение (TSxxxx)`, клик по строке переводит курсор в редактор. На вкладке «Решение» (read-only) diagnostics не считаются.

➡️ **Рекомендация:** (a) и описанные детали.

### Q6 — Язык сообщений об ошибках TS

Весь UI на русском (решение карты), а сообщения TS по умолчанию английские. В пакете TypeScript есть официальный перевод `lib/ru/diagnosticMessages.generated.json`, Type Checker может его загрузить, это ещё один JSON с нашего origin. Размер замерим при реализации.

- **(a) Русские сообщения + код** `TS2322`: «Тип "number" не может быть назначен для типа "string". (TS2322)». По коду ошибку легко найти в поиске.
- **(b) Английские сообщения:** их проще гуглить дословно, ничего не нужно грузить дополнительно, но это единственный английский текст в UI.

➡️ **Рекомендация:** (a). Код в скобках закрывает минус с поиском. Если сборка lib не найдёт перевод, Type Checker откатывается на английский, а не падает.

### Q7 — Autocomplete: объём в MVP

## Общий итог

Раунд 1: Q1, Q2, Q3, Q4, Q5, Q7 — по рекомендациям; Q6 — (b), английские сообщения. Остаток (засчитывание Lesson при ошибках типов, куда записать решения) согласован в чате по рекомендациям.

**К вопросу из Q4 «у всех ли браузерных редакторов так».** Да: любой TS-редактор в браузере везёт компилятор TS целиком (TS Playground, Monaco/VS Code Web; StackBlitz/CodeSandbox — так же или на сервере, что нам закрыто ADR-0004). Урезанной сборки TS 6 нет, разобранные lib между сессиями не сохранить. Помогают кэш по content-hash (повторный визит — только старт ~0.5–1 с), узкий набор lib и порядок загрузки (редактор и Compiler первыми). Дальше — только TS 7 в WASM за тем же интерфейсом.

- **Q1:** отдельный Worker на TS 6 через алиас `"typescript-6": "npm:typescript@6.0.3"` + `@typescript/vfs`, без CDN и ATA, своя обвязка CM6, узкий интерфейс.
- **Q2:** Run работает всегда, ошибки типов только подсвечиваются.
- **Q3:** везде `ESNext`; один модуль конфига для Compiler, Type Checker и `codda test`.
- **Q4:** один воркер на сессию, старт после первой отрисовки, при смене Lesson меняется только файл. До готовности — «Проверка типов загружается», при отказе — «Проверка типов недоступна»; редактор и Run работают, повторных попыток нет.
- **Q5:** только ошибки (syntactic + semantic), без suggestions и `noUnused*`; debounce ~300 мс; «Проблемы» — `строка:колонка — сообщение (TSxxxx)`, клик переводит курсор; на вкладке «Решение» проверки нет.
- **Q6:** английские сообщения с кодом `TSxxxx`.
- **Q7:** autocomplete только от TS, при наборе и по Ctrl/Cmd+Space, с видом и `detail`; auto-import, signature help, JSDoc — «MVP, часть 2».
- **Lesson при ошибках типов** засчитывается, если все Lesson Tests PASS; предупреждение в Test Report — «MVP, часть 2».
- **Запись:** ADR-0009, термин Type Checker в `CONTEXT.md`, roadmap «MVP, часть 2».
