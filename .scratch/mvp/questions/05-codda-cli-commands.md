# Команды CLI `codda` — вопросы

Grilling по тикету [05: Команды CLI `codda`](../issues/05-codda-cli-commands.md). Вопросы идут раундами. В каждом раунде собраны вопросы, у которых все предпосылки уже решены. Ответ пишите под строкой «**Ответ:**». Пустой ответ означает, что вы согласны с рекомендацией.

Что уже решено и здесь не обсуждается: инструмент отделён от контента, курс передаётся путём, сборка статическая ([ADR-0006](../../../docs/adr/0006-tool-separate-from-content.md)); раскладка Course и формат ошибок манифеста `<файл>: <путь к полю>: <сообщение>` ([тикет 03](../issues/03-lesson-manifest-schema.md)); один Dependency Artifact на Course из `package.json` + `package-lock.json`, ошибки `npm ci` с префиксом, все Chromium-прогоны блокируют чужие origin'ы ([ADR-0007](../../../docs/adr/0007-dependency-artifact-per-course.md)).

## Раунд 1

### Q1 — Список команд

Из ваших кандидатов (`init`, `test`, `lesson`, `ci`, `deps`) и команд ADR-0006 (`dev`, `build`) предлагаю такой набор на MVP:

| Команда | Что делает |
|---|---|
| `codda init [путь]` | Создаёт скелет Course: `course.yaml`, `package.json`, `.npmrc` (`save-exact=true`), `.gitignore`, один Lesson-пример, который проходит `codda test`. |
| `codda lesson <id> [путь курса]` | Создаёт скелет Lesson (`lesson.md`, `main.ts`, `solution.ts`, `lesson.test.ts`) и дописывает id в `course.yaml` (4.2). |
| `codda test [путь]` | Вся проверка курса (4.1): манифест, зависимости, сборка Dependency Artifact, Starter и Solution в Chromium. Это же и команда для CI (4.3). |
| `codda dev [путь]` | Локальный просмотр курса в браузере, подхватывает правки файлов. |
| `codda build [путь]` | Статическая сборка курса в папку. |

Чего нет:

- **`codda ci`.** CI запускает `codda test`, а затем `codda build`. Отличия CI от локального запуска (например, `npm ci` вместо «поставить, если нужно» — см. Q6) включаются переменной `CI=true`, которую выставляют все CI-системы. Отдельная команда означала бы две проверки, которые могут разойтись: автор локально видит зелёный, а CI красный.
- **`codda deps`.** Dependency Artifact собирается сам внутри `test`, `dev` и `build` с кэшем по hash (ADR-0007). Отдельно автору его собирать незачем. Ошибки зависимостей показывает `codda test`.

➡️ **Рекомендация:** пять команд из таблицы, без `ci` и `deps`. Их можно добавить позже, когда появится конкретная потребность.

### Q2 — Аргумент «путь» и запуск «в любой папке»

ADR-0006 передаёт курс путём, а вы хотели запускать CLI в любой папке. Варианты:

- **(a)** Путь необязателен, по умолчанию текущая папка. В ней должен быть `course.yaml`, иначе ошибка «здесь нет курса».
- **(b)** Как (a), но если `course.yaml` в папке нет, `codda` ищет его вверх по родителям, как `git` ищет `.git`. Тогда `codda test` можно запустить из папки Lesson.

Отдельно: если путь (явный или текущая папка) указывает на папку Lesson, `codda test` проверяет **только этот Lesson** (плюс общий манифест Course). Это ускоряет цикл автора, который правит один Lesson.

➡️ **Рекомендация:** (b) и проверка одного Lesson по пути к его папке. Пример: `cd courses/react-hooks/use-state && codda test` проверяет только `use-state`.

### Q3 — Как курс попадает в приложение

От этого зависят `dev`, `build` и `test`. Сейчас (PoC) уроки импортируются в код приложения (`courses/index.ts`), и Vite собирает их вместе с UI.

- **(a) Инструмент собран заранее, курс — данные.** UI и Runtime собираются один раз (`vite build` в этом репозитории, позже — содержимое npm-пакета `codda`). `codda build` копирует готовый UI и кладёт рядом данные курса: `course.json` (Course, Lesson, Instructions, Starter, Solution, Lesson Tests) и `deps/<hash>/`. UI загружает `course.json` через `fetch`. `codda dev` раздаёт ту же папку локальным сервером и пересобирает `course.json` при изменении файлов. Vite в момент сборки курса не нужен.
- **(b) Vite собирает инструмент вместе с курсом.** `codda build` и `codda dev` программно запускают Vite, а курс подключается виртуальным модулем. HMR бесплатно, но каждый `codda build` пересобирает весь UI, а у будущего пакета `codda` в зависимостях окажется Vite со всеми плагинами.

➡️ **Рекомендация:** (a). Граница ADR-0006 проходит буквально по формату `course.json`, `codda test` проверяет ровно те файлы, которые потом попадут на хостинг, а вынести курсы в отдельный репозиторий получится без переделок. Цена: в `codda dev` нет HMR, при правке файла курса страница просто перезагружается. Так как это трудно отменить и неочевидно без контекста, предлагаю записать решение в ADR.

### Q4 — Как `codda test` выполняет Lesson Tests

ADR-0007 требует Chromium. Предлагаю так:

1. `codda test` делает то же, что `codda build`, но во временную папку (`.codda/test/`).
2. Поднимает локальный HTTP-сервер на `127.0.0.1` со случайным портом.
3. Через Playwright запускает **полный** Chromium (не `chrome-headless-shell`, по той же причине, что и в `vite.config.ts`: только в нём Sandbox работает в отдельном процессе). Все запросы не на этот origin блокируются и считаются ошибкой.
4. Открывает служебную страницу собранного UI (например, `/#/__codda-test`). Она по очереди выполняет Run из того же Runtime для каждого Lesson: сначала Solution, потом Starter. Test Report возвращаются в Node.
5. Lesson выполняются последовательно в одной вкладке: Compiler прогрет после первого Run, поэтому лимит в 5 с не срабатывает на холодном старте.

Альтернативы: vitest browser mode (тянет Vite в рантайм CLI, см. Q3) или jsdom/Node (запрещено ADR-0007).

➡️ **Рекомендация:** схема выше. Служебная страница входит в обычную сборку, но в UI ссылок на неё нет.

### Q5 — Откуда берётся Chromium

Playwright по умолчанию скачивает браузер с CDN Microsoft. В закрытом контуре (ADR-0002) это не работает. Варианты:

- **(a)** `playwright install chromium` с `PLAYWRIGHT_DOWNLOAD_HOST`, указывающим на внутреннее зеркало. Версия Chromium зафиксирована версией Playwright.
- **(b)** Использовать Chrome, установленный в системе (`channel: "chrome"`), и путь из переменной `CODDA_CHROME`, если он лежит в другом месте. Ничего не скачиваем, но версия браузера у всех разная.
- **(c)** (a) по умолчанию, (b) как запасной вариант через `CODDA_CHROME`.

Если Chromium не найден, `codda test` выдаёт одну строку с командой, которая его ставит.

### Q6 — Кто ставит `node_modules` курса

ADR-0007: в CI выполняется `npm ci`. Локально `npm ci` на каждый `codda test` стирает `node_modules` и стоит десятки секунд.

- **(a)** `codda` сам запускает npm: при `CI=true` всегда `npm ci`; локально `npm ci` только тогда, когда `node_modules` нет или `node_modules/.package-lock.json` не совпадает с `package-lock.json`.
- **(b)** `codda` npm не запускает. Если `node_modules` нет или они устарели, это ошибка «запустите `npm install`». В CI `npm ci` — отдельный шаг пайплайна.

➡️ **Рекомендация:** (a). Одна команда работает и в свежем клоне, и в CI. Ошибки npm показываются как решено в ADR-0007.

### Q8 — Что значит «Lesson прошёл `codda test`»

Проверки по порядку. Если одна упала, следующие для этого Lesson не выполняются:

1. Манифест Lesson валиден (тикет 03).
2. **Solution:** Test Report вида «тесты», в нём хотя бы один тест и все PASS. Ошибка компиляции, runtime-ошибка, timeout или ноль тестов — ошибка.
3. **Starter:** Test Report вида «тесты», и хотя бы один тест FAIL. Если все PASS — ошибка «Starter уже проходит все тесты». Если Starter не компилируется, падает при импорте или зависает — тоже ошибка: студент на первом Run увидит поломку, а не задание.

Проверка Dependency Artifact (сборка, «работает в браузере» из ADR-0007) идёт один раз на Course до Lesson. Если она упала, Lesson не проверяются.

➡️ **Рекомендация:** так, как выше.

### Q12 — `codda init`

```
codda init [путь]          # по умолчанию текущая папка
```

- Папка должна быть пустой (разрешён только `.git`). Иначе ошибка, ничего не перезаписывается.
- Без интерактивных вопросов. `id` Course — имя папки (если имя не kebab-case, ошибка с подсказкой). `title` равен `id`, автор потом правит его в `course.yaml`.
- Создаётся: `course.yaml` (один Module «Основы» с одним Lesson `hello`), `package.json` (`"private": true`, пустые `dependencies`), `.npmrc` (`save-exact=true`), `.gitignore` (`node_modules/`, `.codda/`, `dist/`), `hello/` из шаблона `codda lesson` (Q13).
- Затем выполняется `npm install`: без зависимостей он только создаёт `package-lock.json` и в сеть не ходит.
- В конце печатается подсказка: `npm install react react-dom @types/react @types/react-dom` (если нужен React) и `codda test`.

➡️ **Рекомендация:** так, как выше. Шаблон курса без React: курс может быть и не про React, а пустые зависимости не тянут сеть при `init`.

### Q13 — `codda lesson`

```
codda lesson <id> [--module <title>] [--tsx]
```

- Запускается внутри Course (поиск `course.yaml` вверх, как в Q2). `id` в kebab-case. Если папка с таким именем уже есть или id уже есть в `course.yaml`, это ошибка.
- По умолчанию Lesson дописывается в конец последнего Module, а `--module <title>` выбирает Module по точному названию. Неизвестный Module — ошибка, новый Module не создаётся. `course.yaml` правится с сохранением комментариев и форматирования.
- Шаблон по умолчанию — `.ts` без зависимостей: Starter экспортирует функцию-заглушку, Solution её реализует, `lesson.test.ts` содержит два теста. Starter проваливает хотя бы один из них, так что свежий Lesson сразу проходит `codda test`. `lesson.md` получает `title: <id>` и подсказку в теле.
- `--tsx` даёт шаблон компонента на React. Если `react` нет в `dependencies`, это ошибка с командой `npm install`.

➡️ **Рекомендация:** так, как выше.

### Q14 — `codda dev`

```
codda dev [путь] [--port <n>]      # по умолчанию 127.0.0.1:4173
```

- Печатает URL, браузер сам не открывает.
- Следит за папкой Course, кроме `node_modules/`, `.codda/` и `dist/`. Правка файла Lesson или `course.yaml` пересобирает `course.json`, и открытая страница перезагружается (через Server-Sent Events). Workspace студента в браузере при этом не сбрасывается, как и при обычной правке Starter (тикет 03).
- Если меняется `package.json` или `package-lock.json`, то при необходимости выполняется npm (Q6) и пересобирается Dependency Artifact. Пока он собирается, перезагрузки нет.
- Ошибки манифеста печатаются в терминале в формате `codda test`. Если манифест Lesson невалиден, UI вместо этого Lesson показывает страницу с ошибками, остальные Lesson работают. Если сломан сам `course.yaml`, ошибки показываются на весь экран.
- Lesson Tests сам не запускает: это делает автор кнопкой «Запустить тесты» или командой `codda test`.

➡️ **Рекомендация:** так, как выше. Режим «Lesson с ошибками показывается, а не пропадает» нужен только в `dev`. `build` таким не занимается (Q15).

### Q15 — `codda build`

```
codda build [путь] [--out <папка>]  # по умолчанию <курс>/dist
```

- Проверяет манифест и собирает Dependency Artifact. Lesson Tests не запускает: в CI перед ним идёт `codda test`.
- Любая ошибка манифеста или зависимостей — код выхода `1`, и ничего не пишется. Частичной сборки без сломанных Lesson нет.
- Папку `--out` очищает, только если в ней лежит прошлая сборка `codda` (файл-маркер `.codda-build`). Если папка непустая и маркера в ней нет, это ошибка, чтобы случайно не стереть `--out ~`.
- Все URL внутри сборки относительные, поэтому её можно выложить по любому пути (`/`, `/courses/react-hooks/`). Флага `--base` нет.
- Один курс — одна сборка. Каталога из нескольких курсов в MVP нет.

➡️ **Рекомендация:** так, как выше.
