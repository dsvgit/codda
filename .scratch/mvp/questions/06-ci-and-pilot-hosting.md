# CI, хранилище Dependency Artifacts и хостинг пилота — вопросы

Grilling по тикету [06: CI, хранилище Dependency Artifacts и хостинг пилота](../issues/06-ci-and-pilot-hosting.md). Вопросы идут раундами. В каждом раунде собраны вопросы, у которых все предпосылки уже решены. Ответ пишите под строкой «**Ответ:**». Пустой ответ означает, что вы согласны с рекомендацией.

Что уже решено и здесь не обсуждается: сборка статическая, курсы в MVP лежат в этом репозитории в `courses/`, граница «инструмент ↔ курсы» проверяется в CI ([ADR-0006](../../../docs/adr/0006-tool-separate-from-content.md)); один Dependency Artifact на Course в `deps/<hash>/`, в MVP он вшивается в бандл, CORS не нужен ([ADR-0007](../../../docs/adr/0007-dependency-artifact-per-course.md)); `codda build` кладёт готовый UI, `course.json` и `deps/<hash>/` в одну папку ([ADR-0008](../../../docs/adr/0008-prebuilt-tool-course-as-data.md)); CI = `codda test`, затем `codda build`, поведение CI включается `CI=true`; Chromium ставится через внутреннее зеркало Playwright ([тикет 05](../issues/05-codda-cli-commands.md)). Прогресс и Workspace хранятся только в браузере.

### Q2 — Что запускается на каждый PR

Один пайплайн на весь репозиторий, потому что инструмент и пилотный курс лежат вместе (ADR-0006):

1. `npm ci` в корне.
2. `npm run typecheck`, `npm test` (vitest), `npm run test:e2e` (Playwright).
3. Проверка границы ADR-0006: код инструмента не импортирует ничего из `courses/`. Это правило линтера или отдельный скрипт; решает фича `lesson-manifest`.
4. `CI=true node cli/codda.ts test courses/react-hooks`.
5. `node cli/codda.ts build courses/react-hooks`. Сборка проверяет, что выкладывать есть что, а её результат в PR никуда не выкладывается.

Без фильтров по путям: правка UI может сломать курс, правка курса — e2e. Merge в `main` разрешён только при зелёном пайплайне.

### Q3 — Хранилище Dependency Artifacts

В целевой архитектуре roadmap артефакты лежат в отдельном immutable-хранилище по hash. В MVP транспорт как в PoC (ADR-0007), артефакт один на Course и лежит внутри сборки. Варианты:

- **(a) Только внутри сборки.** `deps/<hash>/` живёт в выходе `codda build` и выкладывается вместе с ним. Отдельного хранилища нет. Между запусками CI ничего не кэшируется: `npm ci` и esbuild для одного курса стоят десятки секунд.
- **(b) Внутри сборки + кэш CI.** То же, но `.codda/` курса сохраняется кэшем CI с ключом по hash артефакта. Экономит те же десятки секунд, но добавляет настройку кэша и риск отладки «устаревшего кэша».
- **(c) Отдельное хранилище** (S3-совместимое, generic packages в registry). Нужно, только когда артефакты грузятся по URL из Sandbox, то есть после эксперимента 07 («MVP, часть 2»).

➡️ **Рекомендация:** (a). Отдельное хранилище и кэш — в «MVP, часть 2» вместе с экспериментом 07, если Run или CI окажутся медленными.

### Q4 — Куда выкладывается сборка пилота

Варианты:

- **(a) Pages Git-хостинга** (GitLab Pages, GitHub Pages в Enterprise). Деплой — один шаг CI, сервер настраивать не нужно. Заголовки кэширования и MIME задать нельзя или почти нельзя.
- **(b) Существующий внутренний веб-сервер** (nginx и т. п.). CI копирует папку по `rsync`/`scp` с ключом деплоя. Заголовки под контролем, но нужен доступ и секрет в CI.
- **(c) Внутренний S3-совместимый bucket** со статическим сайтом. Похоже на (b), но доступ — ключами bucket.
- **(d) Без хостинга.** Пилотные пользователи клонируют репозиторий и запускают `codda dev`. Это нагружает пилотных пользователей тем, что должен делать инструмент, и они видят не ту сборку, что проверил CI.

Требования к любому варианту:

- **HTTPS или `localhost`.** Проверка `integrity` (sha384) через `crypto.subtle` работает только в secure context. По голому `http://` на внутреннем хосте Worker не сможет проверить артефакт.
- `.wasm` отдаётся с MIME `application/wasm`.
- Доступ только из внутренней сети (ADR-0002).

➡️ **Рекомендация:** (a), если Pages у хостинга из Q1 есть и работают по HTTPS. Иначе (b). Выбор зависит от ответа на Q1. Если в Q1 появится что-то неожиданное, вопрос вернётся во втором раунде.

**Ответ:**
в нашем случае будем выкладывать на gihub pages, хостится будем на github

### Q5 — Кто и когда обновляет пилот

- **(a) Автоматически при merge в `main`.** Последний зелёный `main` всегда на пилоте. Откат — revert и новый пайплайн.
- **(b) Вручную:** отдельная ручная job или тег `pilot-*`. Пилот не меняется под пользователями без решения человека.

Если Author поменял Starter во время пилота, у студента с сохранённым Workspace остаётся старый код до Reset. Плашка «Starter обновлён» — уже кандидат в roadmap, в MVP её нет.

➡️ **Рекомендация:** (a). Курс один, пользователи внутренние, а исправления по обратной связи пилота должны доезжать сразу. Ручная кнопка добавляется одной строкой, если понадобится заморозка.

### Q6 — Стабильный origin и доступ

Прогресс и Workspace лежат в `localStorage`, а он привязан к origin. Если в середине пилота сборка переедет на другой хост или порт, у всех пропадёт прогресс.

- Адрес пилота выбирается один раз и не меняется до конца пилота.
- Входа нет: сборка статическая, а в MVP нет backend. Доступ ограничивается сетью (Q4). Если Pages требуют SSO хостинга, это не мешает.
- Если на одном origin окажутся два курса (Q2), ключи `localStorage` уже должны содержать `id` Course. Это требование к фиче прогресса, а не к хостингу.

### Q7 — Сборка работает из любого подпути и без rewrite-правил

На Pages сборка обычно живёт под подпутём (`https://pages.example/codda/`), а не в корне домена. А Pages не умеют отдавать `index.html` на любой путь (SPA fallback). Сейчас в `vite.config.ts` `base` по умолчанию `/`, роутинга нет.

- Все URL в сборке относительные: `base: "./"` в Vite, `fetch("course.json")`, `deps/<hash>/…`, `esbuild.wasm` — относительно страницы, без ведущего `/`.
- Адрес Lesson — во фрагменте: `#/use-state`. Тогда любая ссылка на Lesson открывает тот же `index.html`, и хостингу не нужны rewrite-правила. `codda test` проверяет сборку, открытую по подпути, а не из корня.

➡️ **Рекомендация:** так, как выше. Схема URL (что идёт после `#/`) — решение фичи навигации, здесь фиксируется только «фрагмент, не путь».

### Q8 — Кэширование после обновления

Файлы UI и `deps/<hash>/` уже содержат hash в имени. Но `index.html` и `course.json` его не содержат. Pages (и многие серверы по умолчанию) отдают их с заголовками, при которых браузер может показать старую версию.

- UI загружает `course.json` с `fetch(…, { cache: "no-cache" })`: браузер каждый раз спрашивает сервер, изменился ли файл.
- Старые `deps/<hash>/` при выкладке не сохраняются. Если вкладка открыта до деплоя, а `deps/<hash>/` уже удалён, Run показывает «Курс обновился, перезагрузите страницу», а не непонятную сетевую ошибку.

➡️ **Рекомендация:** так, как выше. На свой сервер (Q4b) дополнительно поставить `Cache-Control: no-cache` для `index.html` и `course.json` и `immutable` для остального.

### Q10 — GitHub.com и ADR-0002

Ответ на Q4 расходится с двумя прежними решениями.

- **ADR-0002** требует полностью внутреннюю инфраструктуру. На github.com раннер Actions ставит пакеты из npmjs.org и берёт образ Playwright из `mcr.microsoft.com`. Часть ADR-0002 про браузер всё равно выполняется: UI, `esbuild.wasm` и артефакты отдаются с одного origin `*.github.io`, сторонних хостов нет.
- **Q6** ограничивал доступ внутренней сетью. Сайт на GitHub Pages открыт всему Internet. Исключение — private Pages в GitHub Enterprise Cloud. Кроме того, на бесплатном плане Pages работают только для публичного репозитория.

Варианты:

- **(a) Уточнить ADR-0002.** Правило для браузера («всё с нашего origin, сторонних хостов нет, проверяется e2e») — это свойство `codda`, оно действует везде. «Закрытый контур» (внутренние registry, раннеры, хостинг) — свойство конкретной установки. Его обеспечивает GitLab-шаблон, а пилот этого репозитория на github.com под это правило не попадает. Курс React Hooks не секретный, поэтому пилот на публичном адресе допустим. Репозиторий публичный или на платном плане, это решаете вы.
- **(b) Пилот должен быть закрытым.** Тогда нужен GitHub Enterprise (private Pages или GHES внутри сети) либо выкладка во внутренний S3 по GitLab-шаблону.

➡️ **Рекомендация:** (a). Нужно ответить ещё на два вопроса: репозиторий публичный? Публичный адрес пилота допустим?

### Q13 — Job выкладки

Выкладка — отдельная job после зелёных проверок, только на push в `main`. Проверки и выкладка используют одну и ту же папку `dist/`: job проверки сохраняет её как артефакт CI, job выкладки забирает. Пересборки нет, так что выкладывается ровно то, что проверили.

- **GitHub:** `actions/upload-pages-artifact` + `actions/deploy-pages`, environment `github-pages`. Pages включаются в настройках репозитория (Source: GitHub Actions), это делаете вы. Заголовки кэша задать нельзя (GitHub Pages ставит `max-age=600`), это покрывает решение Q8.
- **GitLab:** `aws s3 sync dist/ s3://$CODDA_S3_BUCKET/ --delete` с `AWS_ENDPOINT_URL` для S3-совместимого хранилища. Ключи берутся из protected-переменных CI. Для `index.html` и `course.json` отдельный `aws s3 cp` ставит `Cache-Control: no-cache`, для остального — `immutable`. Образ job'ы выкладки (с `aws`) тоже плейсхолдер. Требование HTTPS (Q4) в комментарии шаблона.

➡️ **Рекомендация:** так, как выше. GitLab Pages как альтернативу в шаблон не добавляем. Если понадобится, это ещё одна job.

### Q14 — Pull request в `main` и правило «мелкие правки прямо в `main`»

Вы хотите, чтобы изменения попадали в `main` через PR. В `CLAUDE.md` сейчас написано: «Мелкие правки без тикета — прямо в `main`». Варианты:

- **(a) Всё через PR.** Branch protection на `main` требует PR и зелёный CI, push напрямую запрещён. В `CLAUDE.md` и `docs/ai-workflow.md` правило меняется: мелкая правка идёт отдельной веткой `fix-<slug>` и PR. Агент создаёт PR через `gh pr create`, merge делаете вы.
- **(b) PR для тикетов, мелкие правки напрямую.** Branch protection с обходом для администратора. На push в `main` CI всё равно прогоняется, и красный push не выкладывается. Но проверка идёт после факта, а не до.

Branch protection включаете вы в настройках GitHub, агент описывает их в `docs/`.

➡️ **Рекомендация:** (a). Каждый push в `main` выкладывается на пилот, поэтому проверка до merge важнее, чем лишняя ветка для опечатки.

- **Q12:** GitHub — контейнер `mcr.microsoft.com/playwright:v<версия>-noble`. GitLab — плейсхолдер `$CODDA_IMAGE` для внутреннего образа с Node 24 и Chromium. Registry задаётся `.npmrc` курса. Версию Playwright `codda init` вписывает в шаблон.
- **Q13:** выкладка — отдельная job после зелёных проверок, только на push в `main`. Выкладывается тот же `dist/` из артефакта CI, без пересборки. GitHub — `upload-pages-artifact` + `deploy-pages`. GitLab — `aws s3 sync --delete` с `AWS_ENDPOINT_URL` и protected-переменными, `Cache-Control: no-cache` для `index.html` и `course.json`, `immutable` для остального.
- **Q14:** (a). Всё идёт в `main` через PR, включая мелкие правки (ветка `fix-<slug>`). Branch protection требует PR и зелёный CI. Агент открывает PR через `gh pr create`, merge делает человек. Правило в `CLAUDE.md` и `docs/ai-workflow.md` меняется.
