# codda

Платформа интерактивных курсов по программированию: студент читает задание, правит код в браузере, жмёт **Run tests** и получает PASS/FAIL. Весь код студента компилируется и исполняется **в браузере**, на собственном runtime, внутри полностью внутренней инфраструктуры.

Текущая стадия: **Golden Path PoC завершён (GO)**, итог — `docs/poc-report.md`, спека и тикеты — `.scratch/golden-path-poc/`. Следующая стадия — MVP: `docs/roadmap.md`, шаги — `docs/HOW-TO-PROCEED.md`.

## Процесс

Работа идёт по тикетам через скиллы `mattpocock-skills`: `/clear` → `/implement <тикет>` → `/tdd` → `/code-review` → `## Comments` и `Status` тикета → коммит. Решение или правило, всплывшее в разговоре, сразу записывается в файл: правило — сюда, термин — в `CONTEXT.md`, архитектура — в ADR, задача на будущее — в roadmap. Ветку агент создаёт сам: перед первой записью в файлы фичи (обычно на `/to-spec`, когда известен slug) или на `/implement`, если сессия на `main`, — `git switch -c <feature-slug>` от `main`, имя как у папки в `.scratch/`; тикет из `.scratch/misc/` — ветка `misc-NN-<slug>`. Уже на нужной ветке — остаётся на ней. В `main` всё попадает только через pull request, мелкие правки тоже: ветка `fix-<slug>` от `main` → `gh pr create`; merge делает человек, branch protection требует зелёный CI (каждый push в `main` выкладывается на пилот). Работа вне тикета: если по правилу «Тикет или нет?» из `docs/ai-workflow.md` ей нужен тикет — до кода предложить его оформить. Весь процесс, соглашения и роли — `docs/ai-workflow.md`.

Grilling (`/grilling`, `/grill-with-docs`) ведётся в файле, а не в чате. Каждый раунд дописывается в `.scratch/<effort>/questions/NN-<slug>.md`, где имя совпадает с файлом тикета (`NN` — его номер; grilling без тикета, например по карте, получает `00-`). Образец — `.scratch/mvp/questions/03-lesson-manifest-schema.md`. В файле: вопрос, рекомендация `➡️`, строка `**Ответ:**`. Пустой ответ означает согласие с рекомендацией. В чат идут только ссылка на файл и список вопросов раунда в одну строку каждый. Человек отвечает в файле, а агент читает ответы оттуда и дописывает следующий раунд.

## Жёсткие ограничения

- Никаких внешних сетевых зависимостей в runtime: ни CodeSandbox/Sandpack, ни CDN (unpkg, jsDelivr, esm.sh), ни npmjs.org. Всё, что грузит браузер, отдаётся с нашего origin. См. `docs/adr/0002-*`.
- Код студента исполняется только в `<iframe sandbox="allow-scripts">` **без** `allow-same-origin`. Общение с parent — только через `postMessage` с проверкой формы сообщения. См. `docs/adr/0003-*`.
- Компиляция — `esbuild-wasm` в Web Worker. `.wasm` отдаётся локально (`wasmURL`), не с CDN.
- Скоуп текущей стадии фиксирован в спеке. Не добавлять ни одной функции, которая не нужна для прохождения одного задания от начала до конца.

## Тесты

- **Только для стадии PoC:** на каждом шаге реализации — один простой happy-path тест, написанный до кода и увиденный красным (red → green). Прочие кейсы (ошибки, граничные случаи) не тестируем по ходу, а записываем в `## Comments` тикета на отдельный проход.
- После PoC (MVP и дальше) требования к покрытию строже: ошибки и граничные случаи тестируются в рамках самого тикета. Правило выше на MVP не переносить.

## Agent skills

### Issue tracker

Локальный markdown в `.scratch/<feature>/` (spec.md + issues/NN-*.md). См. `docs/agents/issue-tracker.md`.

### Triage labels

Метка — значение `Status:` тикета, названия канонические. См. `docs/agents/triage-labels.md`.

### Domain docs

Single-context: `CONTEXT.md` + `docs/adr/` в корне репозитория. См. `docs/agents/domain.md`.
